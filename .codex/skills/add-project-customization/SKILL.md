# 项目 Rule/Skill 定制

本方法是客户项目内的显式维护方法，不是新的研发 Workflow，也不替代普通需求、设计、开发或问题处理流程。它只处理客户明确要求“通过 ADD”新增、修改、删除、管理或投影，且可表达为**完整 Rule 文件或完整 Skill 目录**的项目定制。

## 1. 触发与排除

同时满足以下条件才进入本方法：

1. 客户明确要求通过 ADD 管理本次内容，而不是 Agent 根据对话自行推断；
2. 对象是项目拥有的完整 Rule 或 Skill；
3. 本次目标、对象和影响范围足以形成可确认的完整候选。

普通问答、需求、设计、开发、Debug、临时修改、一次性说明和 Agent 偶然发现继续普通流程；可以提出建议，但不启动项目定制盘点、不写 `.add/project`、不重新生成 Host 投影。已经投影的项目 Rule/Skill 仍按既有加载规则用于普通流程，不因未触发本方法而禁止读取。意图语义歧义或超出完整 Rule/Skill 能力范围时，先说明差异并澄清；客户没有明确选择本方法时回到普通流程，零自动纳管。

## 2. 输入与对象边界

开始前核对：

- 本次是新增、修改、删除、管理还是重新投影；
- 对象类型、稳定 ID、用途和适用/排除范围；
- 当前项目唯一源、已选择 Host、各 Host 当前投影和可观察的现场修改；
- 新增 ID 是否与 Canonical 单元重名；重名时使用既有 replacement 合同，不创建第二个同名权威；
- 客户是否只授权形成候选，还是已经准备确认精确源变更。

草稿、临时记录和未确认候选不进入项目唯一源。直接修改 Host 投影不自动纳管；只有客户另行明确要求通过 ADD 管理时，才把完整现场内容转换为中性候选。

## 3. 形成并展示完整候选

按对象形成一个完整候选，不做片段注入：

- Rule 是 `.add/project/rules/<rule-id>.md` 的完整文件；
- Skill 是 `.add/project/skills/<skill-id>/SKILL.md` 与可选 `references/**` 的完整目录，`name` 与目录 ID 一致；
- Rule 和 Skill 都给出非空 `description`，逻辑引用必须可解析；
- 删除也以完整源对象为单位，列清源和各 Host 投影，不使用整目录概括授权。

Rule 候选最小格式：

```markdown
---
description: 约束本项目所有外部 API 变更必须同步兼容性说明。
---
# API 兼容性规则

修改外部 API 前，先识别真实消费者和兼容范围。
```

上述示例的源路径是 `.add/project/rules/example-rule.md`；Rule 的 ID 由文件名 `example-rule` 确定，frontmatter 只要求非空 `description`。

Skill 候选最小格式：

```markdown
---
name: example-skill
description: 为本项目生成并核对外部 API 兼容性清单。
---
# API 兼容性核对

列出消费者、旧行为、候选变化、验证和失败恢复。
```

上述示例的源路径是 `.add/project/skills/example-skill/SKILL.md`；frontmatter 的 `name` 必须等于目录 ID `example-skill`，`description` 必须非空。实际 Skill 可以在同一目录增加 `references/**`。

向客户一次展示：ID、description、完整正文或目录清单、精确源路径、所选 Host 的目标与影响、当前现场差异、与官方 ID 的关系，以及失败后的保留结果。没有展示完整内容时，不得把摘要确认解释成源写入授权。

## 4. 确认、写源与投影

1. 客户确认完整候选、精确源路径和所选 Host 影响；候选、路径或现场变化后重新展示受影响部分。
2. Agent 使用 Host 已有文件能力，把经确认的完整文件或目录写入 `.add/project` 唯一源；CLI 不生成、修改、删除或从投影反写该源。
3. 源写入成功后才调用现有 `add config`，只为所选 Host 生成投影差异计划；未选择 Host 和无关客户文件保持不变。
4. 向客户展示精确 ChangePlan；只有当前计划摘要获授权后，才用现有应用参数写入投影。
5. 应用后核对源摘要、每个所选 Host 的实际投影以及未选 Host 的负向不变证据。

Rule 正文保持独立全文；根受管片段只允许派生 ID、description 和投影路径的最小导航。Skill 由各 Host 的原生 Skill 发现面承载。投影是派生结果，不回写成第二份源。

## 5. 验证与交回

交回结果至少包括：

- 本次显式请求、对象 ID/type、description 和精确源路径；
- 客户确认的候选摘要、所选 Host 和影响范围；
- 源实际写入/删除结果与摘要；
- 各 Host 投影计划、应用结果、保留/冲突及未选 Host 不变结果；
- 官方同名 replacement 处理、直接投影现场差异和仍为 unknown 的限制；
- 失败恢复点和下一责任。

静态文件存在不等于 Host 已加载；需要证明运行效果时另做真实 Host 读取与负向未加载验证，不以模型自报代替。

## 6. 失败与恢复

| 情况 | 处理 |
| --- | --- |
| 请求未明确通过 ADD 或不属于完整 Rule/Skill | 说明边界，回到普通流程；不启动定制盘点、不写项目源、不重新生成投影，已投影内容仍按既有规则加载 |
| 候选、源路径、Host 影响或确认不完整 | 保留候选，不写项目唯一源，不启动投影 |
| 源写入失败或写入后摘要不符 | 保留原现场并报告，不启动投影；修正后重新确认源变化 |
| 投影失败、中断或输入摘要变化 | 保留已经确认的源和现役投影，按 journal 恢复或修正后重新生成计划 |
| 投影存在但源不存在 | 保留为现场差异，不从投影自动反写源，也不自动纳管 |
| Host 专属语义无法中性表达 | 标记 conflict，由客户决定保留现场、改候选或放弃，不静默丢失 |
