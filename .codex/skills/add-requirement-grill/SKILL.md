# 需求 grill（原始需求 → EARS 细粒度）

## 何时启用 / 不启用

**启用**：拿到原始需求 / 一句话 / 草图，或修订既有需求、拆分故事、补验收条件时，由 req-analyst 将当前范围问清、拆成可执行的细粒度需求。
**不启用**：特性边界 / 对象-接入-消费者对齐——那走 [`boundary-grill`](../add-boundary-grill/SKILL.md)。两个 grill 分工：**需求 grill 问"要做什么"，边界 grill 问"归谁管、跟谁接"**。

输入包含真实业务来源、既有需求与有效确认（如有）、本次目标/授权范围、当前 Workflow/调用方及需接收成果的下一阶段责任。修订复用既有编号和已确认项，只澄清受影响部分；属于研发 Workflow 时先了解选定编排 Skill 的当前环节与交接，专业直入不重建上游成果。

## 流程

### Step 0：意图收敛（按需）
意图未成形（"想做 X 但没想清"）→ 先做发散—收敛式 brainstorming，再进 grill。该步骤是前置澄清，不替代正式需求分析角色的成果；运行时无对应技能时可由主会话完成对话澄清，但正式需求文档仍须按 Role 委派规则处理。

### Step 1：拿原始需求（IR）
从业务材料 / 一句话 / 草图取一个原始需求。用业务话说，不掺实现。

需求正文只包含目标、使用者、业务行为、范围、验收和外部依赖。技术方案、选型比较、目录布局和接口实现留到设计阶段；讨论过技术方向不等于需求确认，也不能把尚未选择的实现当成需求缺项。客户明确指定的技术约束可注明来源，但不在本阶段展开方案或批准选型。

### Step 2：grill 式逐条追问（核心——膨胀靠这步）
对这个需求逐条追问，问到清晰、挑出模糊：

- 具体要做到什么？成功标准可量化吗？
- 现在谁遇到什么痛点、怎样应对？这次改动让他获得什么可观察价值？
- **采用障碍**：即使做出来，谁可能不采用、为什么？迁移/学习成本、权限或周边依赖中，哪一项真正影响这次范围？
- 哪些情况要覆盖（正常 / 异常 / 边界）？
- 谁用（角色）？
- 这个“角色”是真实的外部 / 组织参与者，还是系统内部模块？内部调度器、数据库、定时器等机制不得包装成虚假用户角色；它们应写成依赖、约束或系统行为。
- 依赖哪些周边？跟别的需求谁先谁后？
- 有没有"待定（TBD）"、含糊词？→ 当场问清或记入待澄清。

按来源分列事实、假设和待澄清：有证据的事实给来源/适用范围；推测写明当前假设、需验证什么、待谁确认。用户未答复时不编市场事实、客户偏好、规模或采用收益，也不把候选实现补成业务决定。提问与需求规模相称，短答足以澄清就继续；不强制小需求写 PRFAQ、发布稿或另走发布流程。

> 🔴 **不许跳过 grill 直接写需求**——漏的模糊点迟早在后面环节炸。

### Step 3：拆 SR（中粒度）
把 IR 拆成几条**可独立分析 / 排期 / 验收**的功能（SR）。

### Step 4：拆 US（细粒度）+ EARS
每个 SR 拆成一个迭代能交付的用户故事（US），每条配 EARS 验收：
`WHEN <事件> THEN 平台应 <可观察行为>` / `平台应 <恒定保证>`。只写对外可观察行为，不写实现。

### Step 5：梳依赖 + 完备性自检
- 把需求间 / US 间依赖梳清，串成端到端故事线。
- 自检：IR/SR/US 三层来源可追溯、目标/验收可观察，正常/异常/负向边界和范围外事项、角色、依赖、采用约束是否齐备。
- 待确认范围不能藏 TBD 或把假设当结论；缺项回 Step 2 定向问清，暂未答复则保留问题/影响/当前假设/待谁确认。仅暂停依赖该缺项的确认与推进，不阻断无关已确认项。

### Step 6：产出

使用 [`references/需求文档模版.md`](references/%E9%9C%80%E6%B1%82%E6%96%87%E6%A1%A3%E6%A8%A1%E7%89%88.md) 的三层编号、Story/EARS 和待澄清字段，按本次创作/修订范围实读适用完整段落。交付 `requirements.md`（IR → SR → US + EARS）与待澄清表，高风险点交有责任的用户决定；已有成果在原 SSOT 修订，不为每次对话造第二份需求。

把当前对象/修订对应的**精确成果版本**（revision/digest）、目标与范围、验收/负向边界、依赖、假设/未决及完整性自检作为 `requirements.md` 项目制品交回调用方/当前 Workflow；记录实际成果与决定来源，不复制另一套需求状态账。

需求成果提交后，主会话必须主动展示确认表并请求人的决定，不能只汇报 draft 或等用户发现未确认。先给成果路径、精确版本、本次 IR 范围、业务结果与验收摘要，再列需求未决项及影响；技术方案问题交后续设计，不列成需求确认的阻塞项。按 [add-delivery-workflow](../add-delivery-workflow/SKILL.md) §5 的需求责任表列出三类责任角色、实际确认人、确认内容、结论、时间和备注；人员未知就询问，不能从岗位、AI Role 或旧记录猜人，也不能自行缩成一个人。用户明确兼任时分别记录各项职责。

已有对本精确版本的真实决定时直接使用原决定，不为保存记录再问一次；尚未决定的角色保持 pending。人可以明确修改、延后、跳过或带风险继续；记录适用范围、理由和下一步，不把这些决定写成 accepted，也不把未答复当作跳过。无适用决定时只暂停依赖本需求的下游；只授权需求分析也必须发起本次成果确认，但不自动开始设计。

需求模板预置 `## 确认记录`。人对精确需求成果作出真实决定后，Host 才调用 `add checkpoint`；任一落点失败都不声称完成。完整语义由 Workflow 的“三处框架级软确认”统一定义，本 Skill 不复制第二套合同。

精确成果版本发生变化时，只提示历史决定对当前对象的适用性待核查，保留历史决定，不自动撤销、不自动阻断；只有人针对新对象作出新决定时才记录替代关系。成果和适用决定交回调用方/当前 Workflow，由其按有效前置与既有授权决定下一步；不固定只能转 boundary，也不自动启动下一角色、设计、编码或发布。只授权本项则到此交回；普通交回按当前流程定位规则接续，不消费外层插问的返回点。

## 与其他技能 / 角色的关系

- **req-analyst 主 SKILL**——req-analyst 用本 SKILL 把原始需求膨胀拆分。
- **前置**：意图未成形先 `brainstorming`。
- **后续**：需求成果由调用方/当前 Workflow 接收；确需边界对齐时消费 [add-boundary-grill](../add-boundary-grill/SKILL.md)，项目架构/返工或其他下一步由选定 Workflow 决定，不在本技能固定串行流程。
- **同样的 grill 追问法也用于"问清初始化要准备什么"**（§9.4），但那是装配语境，不产 requirements.md。

## 失败模式速查

| 错误 | 修正 |
|---|---|
| 跳过 grill 直接写需求 | 回 Step 2 逐条追问，挑模糊点 |
| 编需求 / 场景凑数 | 找不到真实来源就标"待澄清"，不自己填 |
| 拆到 SR 就停（不到 US / 无 EARS） | 拆到 US 细粒度 + 每条 EARS，才是"够" |
| 写实现（类名 / 函数 / 字段细节） | 需求只写"做什么 / 标准 / 依赖"，实现归设计 / 编码 |
| 把系统内部机制写成用户角色 | 明确真实参与者；内部模块改写为依赖、触发条件或系统行为 |
| 未答复便填市场数据、采用结论或冒充人的明确决定 | 保留假设/待澄清及影响，向实际负责人补充缺失决定，不据此推进受影响下游 |
| 小需求被强制写发布稿，或需求完成就自动派下一角色 | 回到本次价值/验收与授权范围，交回调用方/当前 Workflow，由其决定后续 |
