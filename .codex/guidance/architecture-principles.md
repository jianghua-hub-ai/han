# 架构核心原则

> **定位**：跨项目成立的架构决策维度。仓库形态、服务数量、协议、数据技术和平台组件必须由项目事实与 ADR 决定。

## 1. 业务与边界

- 从业务能力、用户旅程、质量属性和责任边界推导模块，不从技术产品清单反推架构。
- 每个模块/服务有明确所有者、输入输出、状态权威和失败责任。
- 有行业标准时优先标准；项目扩展必须声明版本、兼容和退出策略。

## 2. 仓库与交付

monorepo、multi-repo、submodule 或其他组织方式都是项目决策。选择必须说明：

- 模块/仓库职责与所有权；
- 公共契约发布和兼容策略；
- 跨仓变更、CI、版本和回滚责任；
- 开发环境与发布环境如何复现。

ADD 不预设“微服务必须一服务一仓”。

## 3. 接口与通信

- 内外协议由消费者、信任边界和质量目标选择，不默认 HTTP、RPC、消息或进程内调用。
- 每条跨边界契约说明认证、授权、超时、取消、重试、幂等、错误、版本与容量。
- 请求入口、网关、控制面和数据面按项目需要设置；不存在真实职责时不新增组件。
- 公共契约先识别全部消费者，再演进；兼容、迁移和混跑必须有验证证据。

## 4. 数据与状态

- 每类关键状态只有一个权威写入者；缓存、索引和报表是可重建派生视图。
- 事务边界与业务不变量一致；跨边界一致性策略必须说明失败补偿和可观测性。
- 数据模型、迁移、保留、归档、隐私和回退在设计期明确，不交给默认工具行为。

## 5. 变化点与形态

- 真实存在的多实现差异通过接口、策略、适配器、profile 或 project-local 承载。
- 单实现不预造插件系统；出现第二个真实消费者且变化可命名时再提炼共同契约。
- core 不包含某语言、框架、部署形态或产品术语；这些进入已批准 profile。
- 修改一种形态不得破坏其他消费者，公共修复必须列全受影响范围并分别验证。

## 6. 横切治理

身份权限、配置、日志、指标、追踪、审计和安全策略使用项目批准的统一入口。入口可以是库、SDK、平台服务、sidecar 或其他机制；canonical 只要求语义一致、可替换且有所有权。

## 7. 演进与韧性

- 架构变化必须有驱动因素、候选对比、兼容、迁移、回滚、监控和完成判据。
- 关键依赖明确超时、隔离、背压、容量和故障恢复；不以无限重试掩盖不可用。
- 性能和可用性目标来自业务场景与容量证据，不使用母本固定数字。
- 安全、隐私和合规约束优先于便利性；高风险失败默认 fail closed。

## 8. 项目登记项

项目架构入口应登记：能力/模块清单、仓库组织、主要契约、状态权威、信任边界、已启用 profile、检查/发布方式、质量目标和 ADR 索引。未拍板项保持待决，canonical 不提供伪默认值。
