# 编码与实现通用规范

> **定位**：只规定跨语言成立的实现纪律。语言、框架、包结构、命令和版本由项目启用的 profile 与 ADR 补充，不能反向写入 core。

## 1. 可读性与可维护性

- 使用项目已批准的格式化、静态检查和构建工具；不得因个人偏好切换技术栈。
- 命名表达业务含义，避免无上下文缩写；导出接口和公共契约必须有用途说明。
- 函数和模块保持单一职责。复杂度阈值由项目 profile 声明；超过阈值先拆分再提交。
- 优先早返回和显式分支；不得用隐式副作用、魔法值或异常控制正常流程。

## 2. 契约与兼容性

- 先确认消费者和兼容范围，再修改公共接口、事件、数据结构或持久化格式。
- 兼容改动必须同时覆盖生产者、消费者、序列化/反序列化和生成客户端（如有）。
- 删除、重命名或改变语义属于结构性变更，必须先有设计或 ADR，并给出迁移与回退路径。
- 接口只暴露完成职责所需的最小能力；实现细节不得泄漏为跨模块契约。

## 3. 错误、资源与并发

- 错误必须保留根因和可定位上下文；禁止静默吞错、用成功值伪装失败或无界重试。
- 资源关闭权、事务提交权和状态推进权必须唯一；交接时明确所有权。
- 并发行为必须声明取消、超时、幂等、竞态和失败收敛策略。
- 外部输入在信任边界校验；内部不变量由类型、断言或集中校验守住。

## 4. 分层与领域边界

- 业务规则、流程编排、基础设施访问和交付适配分层，禁止把存储或传输对象直接当领域模型。
- 同一业务状态只能有一个权威写入者；派生视图可重建，不反向成为真相源。
- 多形态或多实现差异通过稳定接口、策略、配置或插件承载；核心流程不堆形态分支。
- 项目采用 DDD、CQRS、事件驱动等模式时，必须由实际复杂度和 ADR 支撑，不为模式而模式。

## 5. 测试纪律

- 行为改动必须带能证明该行为的自动化测试；修复缺陷先建立可复现证据。
- 单元测试覆盖局部不变量，集成测试覆盖真实边界，E2E 覆盖关键用户旅程；不以构建成功冒充测试通过。
- 测试应稳定、隔离、可重复；禁止依赖执行顺序、真实时间漂移或不可控外部状态。
- 覆盖率只是信号。优先验证风险、边界、异常、并发、权限和数据一致性。

## 6. 提交前最小自检

- [ ] 改动只覆盖任务声明的文件和行为。
- [ ] 项目 profile 规定的 format / lint / type-check / build / test 已运行。
- [ ] 公共契约、错误路径、资源所有权和兼容性已核对。
- [ ] 新增测试能在改动前失败、改动后通过，或有等价证据说明原因。
- [ ] `git diff` 无调试代码、凭据、生成垃圾和无关格式化。

## 7. 项目实现层

项目入口只登记已批准内容：启用的实现 profile、检查命令、模块边界、公共契约位置和例外 ADR。未拍板项保持未启用，不在 canonical 中给出默认语言或框架。
