# 抽象设计原则

> **定位**：跨项目的对象、边界和扩展纪律。声明式资源、Handler、Manifest 等属于可选 `resource-platform` profile，不是 core 默认模型。

## 1. 从业务对象开始

- 先识别业务对象、稳定属性、允许动作、状态不变量和外部参与者，再选择类、表、接口或消息。
- 动作不是属性，过程记录不是真相源，技术组件不自动等于业务能力。
- 抽象必须能回答“保护了什么变化、谁依赖它、如何验证”；回答不了就不要新增层次。

## 2. 稳定核心与变化点

- 核心流程只保留跨实现稳定的状态推进和契约。
- 语言、部署形态、提供方或产品差异通过策略、适配器、插件、配置或独立模块承载。
- 新增变化项优先新增实现并注册，不修改所有既有分支；确需改核心时先确认这是共性问题。
- 接口按消费者最小需要设计，不把某个实现的数据结构提升为全局协议。

## 3. 多形态隔离

- 去掉某形态后仍成立的规则属于核心；只在某形态成立的规则进入对应 profile 或 project-local。
- 修改一种形态不得破坏其他形态。共性修复必须列出全部受影响消费者并分别验证。
- “目前只有一种实现”不等于可以把实现细节写死进核心，但也不要求为假想未来提前搭空框架。

## 4. SOLID 与简单性

- 单一职责、接口隔离、依赖倒置和开闭原则服务于真实变化，不作为层数指标。
- 优先组合和显式依赖；继承或全局注册只有在语义确实稳定时采用。
- 一次性差异不抽象；第二个真实消费者出现且差异可命名时再提炼共同契约。
- 结构改动与行为改动分开提交和评审。

## 5. 决策检查

- [ ] 对象、属性、动作、状态和所有权是否清楚？
- [ ] 核心与 project-local/profile 差异是否分开？
- [ ] 抽象是否有至少一个真实消费者和可验证契约？
- [ ] 失败、回退、兼容和迁移边界是否明确？
- [ ] 是否存在更简单且同样满足当前需求的方案？

项目若采用声明式资源编排，额外启用 不适用（未选择此方法）；未启用时不得默认使用 Manifest、Handler、FileFetcher 或资源生命周期术语。
