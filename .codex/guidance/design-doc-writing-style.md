# 设计文档写作准则

适用于 `../../.add/project/knowledge/design-workspace/` 下的特性 / 横切 TDD、`../../.add/project/knowledge/design/` 顶层入口文档、`../../.add/project/knowledge/decisions/` 长篇 ADR。不适用于 tasks / requirements / plans 等执行类档案。

## 三条最高准则

1. **语言写给人看**——读得下去、跟得上推理，不是规范堆砌、bullet 罗列、机器口吻。
2. **图有结构、表达明确**——每张图能独立讲一件事，看一眼就懂。
3. **克制代号与链接**——用人话指代，不堆只有作者懂的内部编号（如 `MOD-A-17` / `TMP-5` / `FLOW-03-S7` 这种，首次出现要么展开成人话要么不用）；非必要不过度交叉链接，正文要能独立读懂，链接是给想深入的人的补充、不是正文的替代。

下面六条正面准则是前两条的实现路径（第 3 条够具体，直接照做）。范例只演示写法，不构成项目技术选型、领域术语或目录约束。

---

## 六条正面准则

### 1. 节首直接抛设计点

每节首句就是本节要陈述的事实或要回答的问题，**不导引、不描述结构、不填充**。

读者看到节标题已经知道章节顺序，文字描述一遍信息量为零。

**正面范例**：

```
不断增加的事件类型要怎么持久化？两条路线对比：

| 路线 | 形式 | 新增类型成本 |
|------|------|------|
| 一类型一表 | 各类型使用独立 schema | 改 schema + migration |
| 统一事件表 | `type` 区分类型，差异字段进入 payload | 不改表结构，但应用层要校验 payload |
```

——首句直接抛设计点（"数据库表要怎么落？"），紧跟对比表。无导引。

### 2. 正文只写目标和事实

写设计决策、字段定义、接口契约、流程步骤、约束条件、代价。**不写元描述**——"将讲什么"、"已讲什么"、"接下来要做什么"、"本节回答几件事"等都不写。

陈述句直接给事实，因果连词在线（`由于` `因此` `反之` `换言之` `据此` `从而`），不用空洞动词（"旨在 / 致力于 / 着力于"）、不用博客 hook（"乍一看 / 你可能会问"）、不用 PPT 对偶（"代价 / 收益"切成对偶模块）。

**正面范例**：

```
统一事件表用 `type` 标识类别，payload 保存差异字段；新增事件类型不改表
结构，但写入端必须先通过对应 schema 校验。

该选择降低了数据库强类型约束，换来更低的类型演进成本。项目以按 ID 查询
和按 type 过滤为主时，这个权衡才成立；依赖复杂关联查询时应重新评估。
```

——直陈事实（"Kind 字段记录类型"）+ 因果连词（"该选择的代价是..."）+ 约束融入叙述（不切成"代价/收益"对偶块）。

### 3. 决策走"现状 → 痛点 → 改造 → 效果"

技术决策段四步必须完整，每段 1-2 句即可，不膨胀。

**“现状”指**：现有项目的真实链路和消费者（有现役实现时），或业界既有路径、无本产品时业务实际怎么操作（新建能力时）。现状判断要注明证据；不能把旧文档意图当成代码已实现的事实。

**正面范例**：

```
业界服务间身份认证常见静态令牌、双向 TLS 和 OAuth 2.0 客户端凭据三条
路径。静态令牌难轮换，双向 TLS 只证明工作负载身份，现有授权需求还要表达
调用范围。

项目采用 OAuth 2.0 客户端凭据获取短期 JWT，并在 audience 与 scope 中表达
服务和权限边界。

该方案增加身份提供方和时钟同步依赖，但获得标准化令牌轮换与授权审计能力。
```

——现状（业界三条路径）→ 痛点（现有约束不满足）→ 改造（选定协议与边界）→ 效果（新增依赖和获得的能力）。

### 4. "选 X" 必伴完整方案对比

存在真实技术选型时，三步走：**核适用对标 → 列可行方案 → 选 X + 论证**。已批准约束或只有一个可行接缝时说明依据和兼容边界，不为了格式制造候选或做无关业界调研。

#### 4.1 节首明确业界对标

业界对标本身是**一个完整论证**，不是一个标签。节首回答四件事：

1. **这部分做什么**——一句话定义本节要解决的具体问题
2. **业界哪些做这个**——列出做这类事的产品 / 特性 / 规范
3. **选谁作为对标 + 理由 + 借鉴程度**——选定后明确**借鉴到多深**
4. **对标的设计哲学**——一句话讲清选定对标的核心思想（铺垫 §4.2 方案对比）

**业界对标的五类**（按"本节内容跟业界已有成熟实现的对齐程度"选用）：

| 类型 | 含义 | 举例 | 节首写法 |
|------|------|------|------|
| **整体对标一个产品** | 本特性整体跟对标产品对应，从功能架构到详细设计都可参考 | 工单管理 → Jira / Linear | 点名产品 + 整体哲学（详细设计可大量借鉴） |
| **部分功能对齐一个产品** | 某些功能维度跟对标产品对齐，但定位不同 | 文档搜索 → Algolia / Elasticsearch | 讲清**对齐范围 + 不对齐范围**——避免读者误判产品定位 |
| **单点深度参考一个产品** | 本特性某个子设计借鉴对标产品的相关实现 | 调度 → K8s scheduler framework | 在具体方案中写“参考 X 的 Y 机制” |
| **多产品特性拼合** | 新场景无单一产品完整对标，拼合多个成熟机制 | 配置发布 → GitOps + feature flags + rollout | 列拼合机制 + 拼合后的总哲学 |
| **行业规范对标** | 行业有标准协议 / 规范 | 身份认证 → OIDC / OAuth 2.0 | 点名规范 + 一句话定位 |

**判断选哪类**：

- 业界这件事有**整套成熟方案** → 整体对标或部分功能对齐（看本项目要不要全部对齐）
- 业界某产品**只在某点做得好** → 单点深度参考
- 本项目场景**业界没有完整方案** → 多产品特性拼合
- 行业有**标准规范** → 规范对标

**论证深度跟选型显然程度成反比**：选型显然（只有 1-2 个明显候选）一句话点名即可；选型不显然（多个有效候选）用对照表 + 选定理由。

**紧凑范例（部分功能对齐）**：

```text
本节做“仓内文档全文检索”。搜索相关性排序与高亮参考 Elasticsearch；
不对齐其集群运维与多租户能力，因为本项目的数据量和部署边界不同。
借鉴范围只到分词、字段权重和结果解释，不把产品整体架构作为前提。
```

对标确立后，问题转化为“如何在本项目已拍板的技术栈下实现该哲学”——进 §4.2。

#### 4.2 方案对比表（4 列）

在对标确立的前提下，列出实现该哲学的多种技术路线。**至少列出所有合理候选**，不要只列 2 条就选：

| 列 | 内容 |
|------|------|
| **方案名** | 清晰标签 |
| **实现机制** | 一句话核心机制 |
| **优势** | 多维度具体优点（类型安全 / 性能 / 演进性 / 可移植 等） |
| **劣势** | 多维度具体缺点（同维度展开） |

用"**优势 / 劣势**"（pros/cons），**不用"代价 / 收益"**——架构师评估用 pros/cons，"代价"是商业话术。

#### 4.3 选型结论：场景特征匹配 + 劣势可接受性

紧跟对比表的两段论证：

1. **场景特征匹配**——本项目的哪些具体场景跟选定方案的优势对得上
2. **劣势可接受性**——选定方案的每条劣势在本项目场景下为什么可接受

读者看完应该知道"为什么选 X、为什么不选 A/B"，而不只是"为什么选 X"。

#### 紧凑范例

```
后台任务需要可靠排队，有三条路线：

| 方案 | 实现 | 优势 | 劣势 |
|------|------|------|------|
| 数据库轮询 | 任务表 + `SELECT FOR UPDATE` | 无新增基础设施；事务边界清楚 | 延迟和轮询压力较高 |
| 自建消息队列 | 项目运维消息中间件 | 吞吐高；消费模型成熟 | 新增部署与故障恢复成本 |
| 托管队列 | 云服务提供 | 运维少；弹性好 | 供应商依赖；离线环境不可用 |

项目在已有数据库、任务量有限且需要离线部署的前提下选择数据库轮询。
其劣势由可配置轮询间隔和任务索引控制；若容量评估超过阈值，再以 ADR
重新评估消息队列，而不是在本设计中预留两套实现。
```

——合理候选列全后，用项目事实选择，并正面说明选定方案的劣势为什么可接受。

### 5. 术语首现 = 一句话定义 + 业界对标

首次出现的术语必须给一句话本质定义。项目自造词必须挂在已知概念上。

非通用术语（CAS / OIDC / OCI / DAG 等）首次出现按四要素普及：中英对照 / 业界对照 / 是否需依赖 / 本质。

**正面范例**：

```
Lease（租约）：带过期时间的临时占用权，对标分布式锁的自动失效机制。

CAS（Content-Addressable Storage，内容寻址存储）：业界标准（如 OCI
Distribution Spec / IPFS）。本质是“内容决定地址”——同内容必同摘要，
具体算法和承载方式由项目契约定义。
```

——一句话本质 + 业界对照。

### 6. 图后必跟解释段

每张 PlantUML 图（含 mindmap / activity / sequence 等）后必须有 1-2 段说明：

- 图里画了什么（组件、角色、关系）
- 关键依赖（A 依赖 B 因为...）+ 数据流方向
- 关键顺序（先 X 再 Y 因为...）
- 画法的设计含义（为什么这样画）

**正面范例**：

```
**说明**：图中订单服务拥有状态转换，通知服务只订阅已提交事件。该方向
保证通知失败不会回滚订单；新增通知渠道应扩展订阅端，不进入订单事务。
```

——图后直接给"读图要点 + 决策含义"，不是"上图展示了 XX"这种空泛复述。

## 受控表达要求

设计文档使用清晰、短句和可检查的技术表达：

- 节首先给出本节结论。
- 一句话只表达一个主要意思。
- 一个步骤只表达一个主要动作，并明确执行者。
- 使用主动语态。
- 同一术语始终保持同一含义；首次出现的专业术语先定义。
- 明确区分事实、判断、建议、未知项和待确认项。
- 关键结论必须能追溯到代码、文档、记录或实际验证。
- 删除重复、套话和没有实际作用的修饰。
- ASD-STE100 只作为表达参考，采用约 80% 的严格程度，不做语言合规校验。

本要求只约束设计文档的表达方式，不新增成果类型，不改变设计流程，不替代事实验证、独立评审或责任人确认。

## 文档级硬约束

### A. 自包含

design.md 是永久 SSOT（按 K8s 控制器思想 "desired state"），所有 8 步过程内容**边走边内化**到对应章节——禁引用任何"过程文档"或"工作区脚手架"。临时产物（stories.md / test-plan.md）只作为下游 SKILL 输入，不作为 design 的论据来源。

理由：临时产物会在活动 10 归档；design.md 单文件可被未来任何时点的读者自洽消费。

### B. PlantUML 图直接内嵌 + 渲染兼容铁律

不能只引用外部图片或链接。所有图必须以 ```plantuml ... ``` 形式内嵌在文档里。

🔴 **渲染兼容约束**：

1. **标签禁 `\n`**——某些渲染器（如 Obsidian PlantUML 插件）把含 `\n` 的标签渲成空框。标签一律单行，需要分行用括号 / 分隔符。
2. **禁 `skinparam linetype ortho`**——同样导致空框。
3. **机制类流程图（责任链 / 打分 / 分组等 rectangle 流程）优先用表**——这类图最脆、信息量低；**时序图(sequence) / 类图(class) 渲染稳定**，按 SKILL 该用时序图/类图的地方放心用。
4. **`plantuml -checkonly` 只验语法、验不出空框**——确认标签真渲染出来必须 `plantuml -tpng -o <dir> <file>` 实渲染成 PNG 再看（`-checkonly` 能过、图照样空）。本地 CLI 渲染正常 ≠ 用户渲染器正常，所以按本铁律写（无 \n / 无 ortho）最稳。
5. **mindmap 颜色语法在节点前缀**——`*[#color] 文本`（颜色码紧跟星号后），**不是** `* 文本 [#color]`（颜色码在末尾会被当字面文字显示成 `[#a5d8ff]`、不上色，`-checkonly` 验不出）。

### C. 需求元数据结构化

需求章节用表格列出五要素：需求来源 / 优先级 / 提出人 / 责任人 / 工作量。

**需求来源 = 业务来源**——市场需求 / 竞争力规划 / 客户痛点。参考 `.spec/requirements/inputs/<待填充:requirements-pkg>`。**不是**文档路径 / 不是会议拍板时间。

**需求价值 = 客户视角**——客户解决了什么痛点。**不是**技术收益（"减少耦合 / 提升性能"）。

### D. 4+1 视图全部充实

五个视图（逻辑 / 开发 / 进程 / 物理 / 场景）都要画图 + 写说明，不能只画 1-2 张。

**逻辑视图三层渐进**：业务能力地图（业务模块层）→ 核心对象模型（领域对象层）→ 整体代码框架设计（实现层）。读者从"业务能力（产品看得懂）→ 领域对象（设计师看）→ 代码框架（实现者看）"层层深入。

**系统上下文视图独立成节**：明确本特性在本项目整体中的位置、依赖谁、谁依赖本特性、输入输出契约。

### E. 颜色 legend 全文统一

PlantUML 图配色遵循 6 色约定（legend 放 §附录，不放 §3 顶部干扰阅读）：

| 颜色 | 含义 |
|------|------|
| 黄 `#ffec99` | 本特性主体 |
| 蓝 `#a5d8ff` | 数据源 / 协议依赖 |
| 绿 `#b2f2bb` | 运行时执行依赖 |
| 紫 `#d0bfff` | 基础设施 / 部署底座 |
| 粉 `#fcc2d7` | 用户角色 / 业务特性 |
| 灰 `#e9ecef` | 独立路径 / 隔离域 |

### F. 性能数值占位

P95 / RTT / TPS / QPS / 告警阈值等具体数字必须写 `TBD（待容量评估阶段定）`，保留规格维度（即"哪些指标要测"），不硬编数字。

例外：明确的设计决策（如"100 QPS 限流"）和实现细节（如"前端 10000 条日志缓冲"）保留具体数字。

**"实现基线 vs 目标规格"两类数字区分**（既有项目经验）：

当代码已有实现默认值，但容量评估未完成——区分两类数字：

| 类型 | 含义 | 写法 |
|---|---|---|
| **实现基线** | 当前代码默认值（事实陈述） | 写具体数字 |
| **目标规格** | 容量评估后的上限（设计承诺） | 必 TBD |

例（中性范例：DB 连接池）：

```markdown
DB 连接池：实现基线 10 连接（可配 `max_open_conns`）；
          目标容量上限 TBD（待容量评估阶段定，按典型业务负载 + 数据库类型确定）
```

效果：

- 不破坏"目标 TBD"原则（容量评估未完成时不写死目标）
- 保留实现现状（"基线 10"是事实，读者能从代码 grep 验证）
- 维度本身保留（"DB 连接池"指标不丢）
- 解释 TBD 的依据（按 X / Y 因素测算）

### G. 主轴贯穿

全文必须有一条贯穿主轴，四选一：

| 主轴 | 例 | 适合场景 |
|------|------|------|
| 数据流向 | Flume：Agent → Collector → Store | 系统类设计 |
| 概念演化 | AI Workflow：Workflow → Graph → Loop | 抽象类设计 |
| 对立辨析 | "是 Workflow 还是 Agent？" | 技术选型类设计 |
| 历史演化 | 三阶段递进，每阶段对应一个瓶颈 | 长期项目类设计 |

主轴决定章节顺序，不是事后补的修饰。

### H. Story 详细设计以用户故事为主线

§Story 详细设计章节以"用户故事 / 场景为主线"组织——被多个用户故事共享的基础设施抽到「共享基础」一节先讲，各用户故事讲端到端实现 + 标明用到哪些共享基础。**不按"横切技术能力 / 纵切场景"分两块平铺**（读者看前半堆基础设施时不知道它为哪个故事服务，拼图割裂）。配一张「Story 拼图 / 覆盖度全景」——把特性完整面拆成维度，维度 × Story 矩阵证明无空白、各 Story 怎么拼成完整特性。

涉及页面的场景按模板 §3.2 先写用户动作、页面状态与成功/失败反馈，再设计 §3.3 的 API；逐项核页面承诺是否有真实接口、权限与错误语义支撑。API 不可行时回到该场景修订交互，不让 UX 与接口各成一份不一致的承诺。无页面场景以真实调用方交互代替页面，不虚构 UX。

🔴 **本条只管"组织"，不替代 SKILL 的"每 Story 内部格式"**——[`design-tdd SKILL`](../skills/add-design-tdd/SKILL.md) Step 4 / 模板 §3.3 规定每个 Story 一节、节内固定 4 块（实现设计-时序图 / 类设计-类图 / 接口设计 / 数据结构设计）。**两者必须同时满足**：§H 解决"共享基础抽出 + 用户故事主线"的组织，SKILL Step 4 解决"每个 Story 节内 4 块齐"。🚧 待对齐：标杆范例待 本项目 首批设计文档沉淀后在此登记。

### I. 设计文档不放测试设计详情

design 只放"可测试性设计层"（测试分层策略 / 覆盖率目标 / 关键验证方式）；**详细测试设计（场景 / 用例 / 覆盖率清单）单独 `test-plan.md`**（test-engineer 活动 6 产，见 [`test-design SKILL`](../skills/add-test-design/SKILL.md)）。design §可测试性章节标注"详细测试待 test-engineer 接力 test-plan"即可，不塞具体测试用例。

### J. 结构设计必须明确责任与可实施合同

各 Story 的对象/模块设计必须解释“谁拥有数据与状态、谁执行判断、哪些不变量始终成立、模块靠什么接口协作”。不能只有类型名字、空类图或操作先后清单，让实现者另猜逻辑落点。

- **责任与状态归属**：说明读写者、状态转换及约束检查的唯一责任位置，避免多个模块各自解释同一规则。
- **接口与协作**：给出与本次实现相称的输入/输出、必要字段或签名、调用方向与异常结果；时序图解释交互，结构图解释职责，二者要能互相核对。
- **变化与复杂度**：识别实际存在的变化点，再说明采用函数、模块、对象或策略接口的依据；简单分支可直接表达，不要求每个条件都改成多态。
- **失败与恢复**：说明失败后哪些状态已经变化、谁清理资源或补偿、调用者怎样得知结果；纯查询/无状态模块明确不适用项，不补造生命周期。

富领域模型、DDD、CQRS 和具体设计模式都是项目可选方案，不是 ADD 的默认架构。已批准选型必须遵循，未知选择不能由写作规范代替决策。自检标准是“能否据此实现、验证责任和异常边界”，不是类的数量或是否使用某个模式。复杂逻辑仍需充分展开，不能借保持简单省略真正需要的对象、接口和数据设计。

### K. 写结论不写过程，保持紧凑 🔒

文档落"**这是什么 / 各管什么 / 为什么这么定（一句）**"的**结论**，不写"我先考虑 X 再改成 Y"的**推导过程**。理由：过程描述白占上下文，读者要的是结论。

- **禁过程叙述**：重构前 vs 重构后对比、"这张图只画了一半然后我补了另一半"、方案探讨推演——这些是"我怎么想出来的"，删；只留最终结构 + 一句 why。（§4 决策的"现状→痛点→改造→效果"是**结论性论证**，不是过程叙述，保留但精炼。）
- **紧凑**：连续空行压成单个；同一意思不重复说；表能说清就不写长段。
- **人话**：技术名词括号里点一下，不当主角；正文是能读懂的中文（见 [`language-preference`](language-preference.md) 说人话）。

### L. 框架类设计：全局骨架 + 完整性自检 🔒

设计一个**框架 / 平台能力**（非单点功能）时：

- **先给全局分层骨架**（完整结构的鸟瞰），再分层展开——不堆零散 Story 让读者自己拼。骨架要让人一眼看到"这个框架由哪几层 / 哪几块组成、各管什么"。
- **完整性自检**：对照真实业务场景过一遍，确认**覆盖全、没漏关键对象 / 场景 / 分支**。常见漏点——只设计了"做一次动作"漏了"持续运行 / 调谐"、只设计正常流漏了并发冲突 / 失败补偿 / 跨实例交互。问自己："去掉这版设计，哪个真实业务跑不起来？"

## 自检流程

写完每节后照以下三问自检：

1. **节首是否直接抛设计点？** 第一句是不是"将讲什么"或"已讲什么"等元描述？是 → 删
2. **每段是否只写事实和决策？** 有没有空洞动词、博客 hook、PPT 对偶？有 → 改直陈
3. **决策是否完整四步？** 现状 / 痛点 / 改造 / 效果有没有齐？选型有没有"为什么不 A/B"？

照六条正面准则的范例段落写，自然不会写出有问题的内容。
