# 技术选型合规性规范

## 1. 通用准则（核心规则，跨项目通用）

### 1.1 核心原则

**严格遵循设计文档技术选型，不得擅自变更**。遇到问题必须在既定技术栈内解决；变更需获得用户明确同意。

### 1.2 执行规则（遇问题时）

1. 在当前技术栈内找方案
2. 查官方文档和社区实践
3. 调整实现方式
4. 仍无法解决 → 向用户说明并申请变更

### 1.3 禁止行为

- ❌ 因报错就切换其他技术方案
- ❌ 未经同意引入未列出的依赖库
- ❌ 用其他实现替代既定技术栈（如随意切换 ORM / 状态管理 / 构建工具 / 测试框架）

### 1.4 需用户确认的变更

- 技术选型兼容性问题
- 引入未提及的第三方库
- 升级或降级版本
- 使用替代方案绕过限制

### 1.5 变更请求格式

```text
⚠️ 技术选型变更请求

当前问题：[具体问题]
设计文档选型：[原定方案]
建议变更为：[新方案]
变更原因：[详细说明]
影响范围：[影响模块]

请确认是否同意此变更？
```

## 2. 项目技术事实的单一依据

canonical 不提供默认技术栈，也不在本 Rule 填写项目技术表。项目“已选技术与版本”只在已有架构/ADR 或项目已登记的 manifest 之一维护权威值，其余位置精确引用该来源；不能两处分别手改同一事实。

读取时核对技术、版本、决策证据和兼容范围，并分清候选、已批准选择与代码实际现状。未知值保持未知；示例、当前工具运行环境和 ADD 自身依赖不构成客户项目选型。

多形态或技术 profile 的差异只在项目实际存在时登记于上述项目依据；单形态不补占位表。各启用代码 profile 的 build/type-check、test、lint、package/release 等适用命令从项目真实入口或已登记配置读取，缺命令说明缺口，不猜一组母本命令。

变更选型时按已授权 ADR/架构变更更新权威和兼容证据，再同步受影响的引用及实现；不能只改某份表格的版本号，也不能为消除不一致擅自升级依赖。
