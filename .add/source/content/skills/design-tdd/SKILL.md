# Design TDD — 特性详细设计

## 何时启用 / 不启用

### 启用：特性级设计（活动 5）

写新特性的**特性设计说明书**时（boundary-grill 已完成 → 进正式 8 步产出）：

- 业务特性 / 横切特性（项目特定特性编号见 项目入口 `<feature>` 占位）
- 跨服务的大型设计任务

**前置依赖**（强制）：[`boundary-grill SKILL`](../boundary-grill/SKILL.md) 必须先完成——5 段叙事 + 4 栏边界已对齐，否则不能进 Step 1。

**产物**：每个特性**唯一一份** `<design-workspace>/<feature>/design.md` —— **特性设计说明书 = TDD = design.md，三者同物**（"特性设计说明书"是正式名 / 模板名，"TDD" 是 SKILL 命名沿用的技术别名）。永久 SSOT。+ `stories.md`（临时，task-decompose 输入）。

### 🔴 不启用：task 级实施不产独立 TDD 片段

**已验证的反例**：为单个 task 另行产出独立 `tdd-fragment.md`，会跟特性 design.md 形成**两份设计文档**——违反 SSOT，归档时还多一份冗余。

🔒 **铁律：一个特性只有一份设计文档（design.md）。task 是它内部的实施切片，不产自己的设计文档。**

task 级实施（活动 7）正确做法：

| 情况 | 正确动作 |
|---|---|
| 特性 design.md 已含 task 所需的字段表 / 接口契约 / 实施要点 | task 实施 G0 必读 design.md 相关章节即可（走 [`task-implementation SKILL`](../task-implementation/SKILL.md)），**不产任何设计片段** |
| 特性 design.md 细节不足以支撑实施 | ❌ 不另造片段——**回活动 5，feature-designer 增量 Edit 补进特性 design.md 对应章节**（design.md 是活的 SSOT，可增量演进） |
| task 改动触及特性边界 / 跨服务契约 | 回活动 4 重 grill 或活动 3 追 ADR |

判断口诀：**缺设计 → 补到特性 design.md，不新建文档**。

## 加载的规则

- [`design-doc-writing-style.md`](../../rules/design-doc-writing-style.md)（写作准则——节首框问题 / 图后释 / 选 X 必伴对比 / 性能数值占位 / 措辞红线）
- [`abstraction-principles.md`](../../rules/abstraction-principles.md)（OO 严格区分对象 / 属性 / 动作；统一流程 + 扩展点）
- [`decisions-guide.md`](../../rules/decisions-guide.md)（设计中遇决策点引导到 ADR）

## 引用与链接规则

- 过程文档与最终文档中引用 reference、产物、图表、代码报告等文件时，必须使用相对路径
- 不允许在生成的 Markdown 文档中写入本机绝对路径
- 若用户输入是绝对路径，读取时可用，但落盘必须转为相对路径

## 全局执行原则

1. **先定位已有成果，再推进设计**
   - 使用项目登记的 `<design-workspace>/<特性名>/`，不覆盖已有 design.md；只有缺失且本次获授权时初始化。
   - 需求/边界/设计各有唯一正文；已有批准设计够用直接复用，真缺口补其受影响章节，不为 task 再建一份设计。

2. **结论直接进入对应正文**
   - 每完成一个小节或关键决策立即更新 design 对应章节或归属 ADR，不另建沟通日志、逐步报告
   - 聊天窗口只输出摘要、关键问题和需要用户补充的内容
   - 内容较长时优先落盘，回复中给出相对文件路径和简要摘要

3. **不确定点优先处理**
   - 不确定点包括：需求描述模糊 / 验收标准缺失 / 规格无量化指标 / 接口未明确 / 与现有代码冲突 / 与模板章节不匹配
   - 每个不确定点必须记录：来源 / 影响章节 / 当前假设 / 风险 / 建议补充问题 / 默认处理策略
   - 优先通过代码搜索、模板查阅、历史文档查阅自行探查；无法得出时才向用户开放式提问

4. **开放式沟通，避免机械确认**
   - 提问聚焦真实不确定点，不要要求用户逐项确认所有模板章节
   - 低风险可逆细节可标明默认假设继续写草稿；接入位置、核心方案或消费者可见行为不能默认拍板
   - 关键规格、破坏性变更、安全 / 隐私 / 兼容性风险、方案重大取舍，必须主动向用户沟通

5. **规格深度处理**
   - 对性能、可靠性、可用性、可服务性、兼容性、安全、隐私、韧性、资源、License、升级等规格，不允许只写"无影响 / 不涉及"，除非已有依据
   - 需按模板要求形成闭环：影响判断 → 依据 → 风险 → 设计措施 → 验证 / 验收建议
   - 缺少量化指标 → 生成"待确认规格项"并给出可执行的推荐指标或默认假设

6. **代码与模板双向对齐到可实施合同**
   - 从目标和约束推导对象、模块、职责、状态、不变量及协作，再映射现有源码与构建/部署结构；不把需求清单或业务阶段表当逻辑模块。
   - 消费者依赖的接口签名、输入输出字段、类型、必填/默认值、校验、错误、版本兼容、数据生命周期在设计中明确。引用已有定义时给路径/修订与适用范围；本次改动逐项说明保留和变化，不能一句“实现时对齐”留给拆任务。
   - 设计合同不等于整段生产实现；内部算法按风险和可实施程度展开。最终与模板适用章节对应，不涉及项给依据；共用合同只在一处定义。

## 自动过程文档目录规范

按 K8s 控制器思想——**desired state（永久）+ controller actions（回收）**：

```text
.spec/design-workspace/<feature-name>/
├── design.md           # 永久 SSOT，含决策追溯顶部段（status 流转 / 默认假设 / 待澄清）
├── stories.md                     # 临时（task-decompose 输入），活动 10 归档
└── boundary.md                    # 永久（由 boundary-grill SKILL 产，含 5 段叙事 + 4 栏边界）
```

**永久 vs 回收**：

| 文件 | 长期定位 |
|---|---|
| design.md | 永久 SSOT，desired state（含决策追溯顶部段） |
| boundary.md | 永久（边界声明） |
| stories.md | 临时 / 活动 6 task-decompose 用完 → 活动 10 归档 |

**取消 logs/ 目录**——按你的洞察：

- 之前 `logs/decision_log.md` 跟 ADR（架构决策）+ design 修订表都有重复
- 之前 `logs/change_log.md` 跟 git log 重复
- 简化：决策追溯**内化到 design 顶部 §决策追溯段**，修订史靠 git log / git blame
- ADR 仍独立（架构级 + alternatives + 按服务归类）
- 不破坏"ADR 不合并到 design 保纯洁"原则——design §决策追溯只记 status 流转 + ADR 级别**以下**的默认假设 + 待澄清；ADR 级别决策仍走独立 ADR 文件，design 仅引用编号

🔴 **取消独立 11 过程文档（00-11_*.md）**——按"K8s 控制器思想 + 长稳运行"原则：

- 之前 00-11 是写作脚手架，内容跟 design 重叠 → 归档浪费 / 过程信息丢
- 现在：feature-designer 边走 Step 1-8 边**直接更新 design 对应章节**（不产独立 00-11 文件）
- 决策追溯内化到 **design.md 顶部 §决策追溯** 段（不开 logs/ 子目录）
- 唯一例外：`stories.md` 因是 task-decompose SKILL 输入，临时独立

**design.md frontmatter 必含字段**（借鉴 K8s KEP stages）：

```yaml
---
feature_id: <feature>            # 项目占位映射
title: <一句话>
status: draft                    # draft / implementable / implemented
created: YYYY-MM-DD
last_updated: YYYY-MM-DD
related_adrs:                    # ADR 不复制内容，引用即可（保 design 纯洁）
  - ADR-NNNN <一句话决策>
related_improvements:            # 未来 backlog 引用
  - <improvements/<service>.md#xxx>
---
```

**status 流转**：

- `draft`——feature-designer 写中或用户审视中
- `implementable`——design 通过用户 Gate，task-planner 可拆 task
- `implemented`——已选流程约定的实施、独立评审和实际适用的集成/验收证据齐备；单 task 完成不代表特性完成

每次 status 流转 → design.md 顶部 §决策追溯 §status 流转表追加一行（用户拍板时间 + 当前 commit）。

## 不确定点处理机制

执行任一步骤时维护《不确定点台账》：

| ID | 来源 | 不确定点 | 影响章节 / 设计项 | 已探查信息 | 当前假设 | 风险等级 | 建议问题 | 默认处理策略 | 状态 |
|----|------|---------|--------------|-----------|---------|---------|---------|------------|------|

处理规则：

1. **先探查**：优先读取模板、需求文档、代码、历史设计文档、配置文件、接口定义、部署脚本
2. **再判断**：判断是否能基于已有信息形成合理假设
3. **再沟通**：只有高风险或影响最终方案的点，才集中向用户提问
4. **可默认推进**：低风险或可逆决策可写入默认假设并继续推进
5. **持续闭环**：用户补充后，更新台账状态为"已澄清 / 默认采用 / 延期确认 / 不涉及"

## Step 0：启动与工作区初始化

### 0.1 输入识别

识别用户输入中的：

- 特性名称 / 需求文档路径 / 代码路径 / 目标版本
- 期望输出路径
- 关键约束或已有方案
- 是否已有结构化需求分解文档
- **boundary-grill 产物**（位置：`.spec/design-workspace/<feature>/boundary.md`）

### 0.2 创建工作区

先确认工作区目录 `<design-workspace>/<feature>/` 和已登记设计；不覆盖已有 design.md，修订在其当前正文进行。仅缺失时按授权初始化：

- `design.md`——按模板初始化空骨架（frontmatter `status: draft` + 章节占位）
- **可选 change/spec 载体确认**：只有项目入口显式启用该能力时，才按已登记模板和路径补齐 proposal、指针与 delta；未启用时跳过，不阻塞 design SSOT


🔴 **不创建 00-11 独立过程文档**——所有过程章节内化到 design 对应章节边走边更新。

### 0.3 读取模板与边界依据

- 唯一模板资源：[特性设计说明书模版](references/特性设计说明书模版.md)。模板只定义字段与含义，不授予批准或实施权限。
- **首次设计**：先读目录与适用说明，再完整读取 §1–3、适用 §4–6 及需求分配/引用章节；必要质量维度选中后读取适用完整段落，不凭章节名推演要求。
- **修订**：先核原设计和受影响消费者，只读模板对应适用完整段落及关联接口、数据、异常/DFx 约束；不默认重读整份模板。已有字段直接复用，不新建页面或 task 设计副本。
- **覆盖自检**：Step 8 逐项核目录、适用性、正文落点、需求与验证依据；未涉及项给理由，未读/未决项如实说明，不把标题齐全当完整设计。
- 读 boundary-grill 产物（`boundary.md`），把 5 段叙事 + 4 栏边界搬进 design §1 需求场景概述 / §需求边界 小节

### 0.4 design frontmatter 必含

按 KEP stages 借鉴 + ADR 引用规范：

```yaml
---
feature_id: <feature>
title: <一句话特性目标>
status: draft                    # draft / implementable / implemented
created: YYYY-MM-DD
last_updated: YYYY-MM-DD
related_adrs: []                 # 引用 ADR-NNNN，不复制内容（保 design 纯洁）
related_improvements: []         # 引用 improvements/<service>.md
---
```

### 0.5 design.md 顶部 §决策追溯 段（模板）

frontmatter 之后、第 1 章之前，固定一段 `## §决策追溯`——本特性所有"轻量决策追溯"集中地，含 4 个子表。**ADR 级决策不进这里**（走独立 ADR 文件 + frontmatter `related_adrs` 引用）。

```markdown
## §决策追溯

> 本段是本特性"轻量决策追溯"——status 流转 / 默认假设 / 待澄清 / improvements 引用 4 张表。
> ADR 级决策（架构层 + 跨服务 + 含 alternatives）走 `<decisions-dir>/<service>.md` 独立文件，本段仅在 frontmatter `related_adrs` 引用编号。

### §status 流转

| 日期 | 状态 | 拍板人 | 关联 commit / 事件 |
|---|---|---|---|
| YYYY-MM-DD | draft | feature-designer | 初稿落盘（commit <sha>） |
| YYYY-MM-DD | implementable | <用户> | 设计 Gate 通过（活动 5 → 活动 6） |
| YYYY-MM-DD | implemented | <实际确认人> | 当前流程约定的整体交付与适用验收证据引用 |

### §默认假设（feature-designer 推进时自行采用的）

| ID | 假设内容 | 依据 | 影响章节 | 状态 |
|---|---|---|---|---|
| A1 | <一句话假设> | <代码搜索 / 模板 / 行业惯例> | §3.x | 默认采用 / 已澄清 / 已修订 |
| A2 | ... | ... | ... | ... |

### §待澄清（必须用户拍板的）

| ID | 问题 | 影响章节 | 当前推荐 | 用户结论 | 状态 |
|---|---|---|---|---|---|
| Q1 | <一句话问题> | §3.x | <推荐方案 + 理由> | <待用户> | 待拍板 / 已澄清 |
| Q2 | ... | ... | ... | ... | ... |

### §improvements 引用（识别到但本期不做的优化项）

| 来源活动 | 项 | 跳转 |
|---|---|---|
| 活动 5 设计 | <一句话> | [improvements/<service>.md#item-id] |
| 活动 3 ADR | <一句话> | [improvements/<service>.md#item-id] |
| 活动 8 评审 | <一句话>（reviewer ISSUES → 用户讨论后归此） | [improvements/<service>.md#item-id] |
```

**与 ADR 不重复**——ADR 是架构级决策（含 alternatives / 跨服务影响）；§默认假设是"低风险可逆 + feature-designer 自决"；§待澄清是"高影响必须用户拍 + 还未拍"；§improvements 引用是"识别到但本期不做"。四张表彼此不重叠。

**与 git log 不重复**——git log 是文件级修订史（每个 commit 改了什么）；§status 流转是设计文档生命周期里程碑（draft → implementable → implemented，每阶段最多 1 条记录）。

## Step 1：业务目标、技术约束与特性影响分析

### 1.1 业务目标提取

从《结构化需求分解文档》或用户输入中提取：

- 功能目标 / 场景目标 / 体验目标
- 性能目标 / 可靠性 / 可用性目标
- 安全 / 隐私 / 韧性目标
- 兼容 / 升级目标
- 可服务 / 运维目标
- 验收标准

**写入 design §1 特性需求概述**（含 IR / SR / 验收标准等）。决策点 + 默认假设 → design.md 顶部 §决策追溯 §默认假设表追加一行（含时间 / 决策 / 依据 / 状态）。

### 1.2 技术约束整合

汇总：

- 技术栈约束 / 现网部署约束 / 版本与兼容约束
- 资源与成本约束 / 公共组件依赖约束
- 安全与合规约束

区分：不可突破约束 / 可协商约束 / 待确认约束。

### 1.3 特性影响分析

**写入 design §特性影响分析章节**，覆盖模板中的影响项：

| 影响项 | 分析要求 |
|--------|---------|
| 功能模块重构 | 是否涉及 / 重构范围 / 影响模块 / 迁移策略 |
| 关键资源限制 | CPU / 内存 / 存储 / 网络 / 副本数 / 亲和性 / 扩缩容影响 |
| License 影响 | 是否新增 / 变更 / 授权方式 / 验收方式 / 失败影响 |
| 性能规格影响 | QPS / 响应时间 / 并发 / 容量 / 数据规模 / 压测建议 |
| 可靠性规格影响 | MTBF / MTTR / RTO / RPO / 故障恢复 / 单点风险 |
| 可信影响 | 安全 / 韧性 / 隐私 / 证书 / 认证 / 授权 / 审计 |
| 可用性影响 | 对自身和周边模块可用性的影响 / 降级策略 |
| 可服务性影响 | 日志 / 告警 / 诊断 / 运维命令 / 备份恢复 / 升级回退 |
| 兼容性影响 | API / 数据 / 配置 / 版本 / 部署 / 升级前后兼容 |
| 特性交互冲突 | 与已有特性、重大特性、公共组件的交互和冲突 |

每项必须包含：影响结论 / 依据 / 设计措施 / 验证建议 / 不确定点。

### 1.4 模糊点与开放式提问

模糊点写入 design 顶部 §决策追溯 §待澄清表（待用户拍板的点）。集中询问高影响问题：

```text
我已经先基于模板 / 需求 / 代码做了探查，目前还有几个会影响设计结论的点想跟你确认：
1. ...（说明为什么影响设计）
2. ...（当前默认假设是什么）
这些高影响项未确认前保持待决定；我可继续不依赖它们的设计，不据此进入受影响实施。
```

### 1.5 输出产物

- design.md §1 特性需求概述 + §特性影响分析（边走边更新）
- design.md 顶部 §决策追溯（默认假设 + 待澄清）

## Step 2：方案对齐与 Story 划分（design-tdd 内部步骤，不新增 Skill 或文档）

### 2.1 定向核实现状与场景

先据需求和已确认边界说明本特性接入的现有流程、前后阶段、调用方、消费者、权威数据、主成功路径，以及真正相关的失败、重试、升级、回退、删除和权限场景。只有涉及的场景才展开，不为填表制造分支。

凡判断“当前已经支持什么”或“改变现有行为是否安全”，必须定向读取固定工作区内最新相关代码和真实调用方，重点核实：

- 现有模块和目录结构
- 相关接口定义 / 数据模型 / 配置 / 缓存 Key / 数据库变更方式
- 公共能力：鉴权 / 日志 / 告警 / 任务 / 证书 / 备份恢复 / 升级 / License
- 部署文件：Helm / Kubernetes / Docker / 脚本 / CI / CD
- 测试与验收方式，以及必须保持的正向行为

Wiki 是可选辅助证据，不以安装或可用为设计前提；可用且获准时按当前问题读取。ADR、既有设计用于核对意图和约束，不能代替代码说明实际行为。两类证据冲突时列出差异与待决定项，不静默选边。按问题读取，不全量加载仓库或 Wiki。

将现有链路、证据位置、可复用接缝、冲突与缺口写入同一份 design.md 的场景和总体方案相关章节；不另产代码搜索报告或方案讨论文档。

### 2.2 比较真正需要选择的方案

围绕接入点与核心机制先核拟复用、扩展、替换或删除什么；检查是否制造第二条流程、第二个权威数据源、不必要的新服务，或改变未获授权的消费者行为。只有存在真实可行的不同选择时比较候选，不按子需求强凑方案数。每个实质候选说明：

- 实现思路
- 复用现有代码 / 组件情况
- 规格满足度
- 风险与约束
- 改造范围
- 验证方式

UX/API 在此只核可行性：拟议用户动作、结果和失败反馈能否由现有或拟新增接口、权限及审计支撑；具体交互和字段契约留 Step 4 按 UX → API 顺序设计。规模、时延、一致性和恢复要求只有会改变选型时才参与比较；没有依据的数值保持待确认。

优先推荐"约束贴合度高、复用现有能力多、对兼容性影响小、可验证性强"的方案。

**方案对比写法**：有真实选型时按 [`design-doc-writing-style §4`](../../rules/design-doc-writing-style.md) 说明适用对标、候选的实现/优势/劣势及选择理由；已有批准约束或唯一可行接缝只说明依据，不制造备选。

### 2.3 核心方案集中确认

把目标场景、接入位置、复用/变更范围、必须保持的旧行为、真实候选取舍和高影响未知项写入 design.md，集中请实际决策人确认核心方案。已确认的方案不反复请示；小参数和低风险可逆细节可明确假设用于草稿。核心方案未确认时，保持受影响章节待定，不据此展开详细实现或进入实施；不依赖该决定的工作可继续。此处的方案确认不替代最终设计 Gate，也不新增框架级确认点。

若拟改变已有**已确认**的消费者可见行为，按需读取 `rule:task-execution-workflow` §4.1 的唯一变更授权定义；方案讨论或设计修订本身不自动取得实施授权。

### 2.4 Story 划分

结合 Use Case 和 INVEST 原则，输出 `stories.md`：

- Story ID / 名称 / 用户价值 / 范围
- 主成功场景与扩展场景
- 验收标准
- 依赖关系
- 纵切 / 横切划分理由
- 不纳入本次范围的内容

### 2.5 输出产物

- 同一份 design.md 的场景、现状证据、总体方案、必须保持的行为和 §3.x Story 列表段（边走边更新）
- `stories.md`（独立——task-decompose SKILL 输入，活动 10 归档）

## Step 3：基于已确认核心方案的总体设计（4+1 视图）

写入 design.md §3 总体设计章节（4+1 视图）。本步确定系统边界、责任与依赖的总体骨架；受 UX/API 联合走查影响的精确接口、模块协作和数据合同在 Step 4 定稿，不因先画结构图而反推或冻结用户交互：

### 3.1 总体设计思路

- 设计目标
- 架构模式
- 设计原则
- 复用与兼容策略

### 3.2 4+1 视图

| 视图 | 内容 |
|------|------|
| 逻辑视图 | 核心对象、属性/动作、状态与不变量；模块/组件职责、层间依赖、接口与数据所有权，不以活动顺序替代结构 |
| 开发视图 | 上述逻辑元素到代码仓/包/目录/文本源及构建产物的映射，编译和测试依赖、允许的引用方向 |
| 进程视图 | 实际执行者、进程/线程或按次调用的生命周期，同步异步、并发共享资源、失败隔离与恢复 |
| 部署视图 | 交付件、安装位置、环境依赖、节点/资源与升级兼容；不为无容器项目虚构 Pod |
| 场景视图（+1） | 用例贯穿对象和模块，展开正常/异常/并发/恢复时序，核前置、状态、后置及可观测证据 |

上下文视图独立表达外部交互方、系统/信任边界；用例作为 §2 与场景视图的输入，不替代开发或进程视图。各视图的元素名称和接口保持一致；未涉及项说明依据，不为凑图制造模块。

### 3.3 可行性验证记录

- 关键技术点
- 代码依据
- 风险
- 验证结论或待验证项

视图中存在信息不足 → 写入不确定点台账 + 默认假设。

## Step 4：Story 级功能设计

实际设计顺序是：先按模板 §3.2 写受影响场景的 UX 动作、状态与反馈，暂不填写其中的“后端 API 对接”栏；再先填写各 Story 的 §3.3「接口设计」，定好支撑交互的公开 API；然后补齐同一 Story 的实现设计、类/组件设计和数据结构设计，最后回填 §3.2 的真实 API 引用并联合走查。最终文档仍按模板 §3.3 的四块顺序呈现（§3.3 对应 "XXX Story 设计"，**不是 §4**——§4 是可靠性/Function Safety），不为写作顺序改模板。不涉及页面时先说明调用方交互及成功/失败可观察结果，不虚构页面。

对每个有界场景，先确定用户动作、页面状态、成功结果、加载/空态/错误/权限不足/重试或取消反馈；再根据这些交互设计 API 的输入输出、权限、错误和必要审计。接口定义后做一次 UX/API 联合走查：每个页面承诺的结果都有接口与失败语义支撑，每个新增接口行为都有真实消费者；不可行时回到该场景修订 UX，不留下两份冲突合同。公开契约按 §4.3 精确到消费者可实施，不能推迟到拆 task 才决定。

🔴 **格式硬约束（项目实践曾因“用户故事叙事 + 组件平铺”被打回）**：**每个 Story 一节，节内固定下面 4 块**（实现设计 / 类设计 / 接口设计 / 数据结构设计）。被多个 Story 共用的底座组件，按 [`design-doc-writing-style §H`](../../rules/design-doc-writing-style.md) 抽到「§3.3.1 共享基础」先讲清接口/数据结构，各 Story 直接引用、不重复贴；Story 专属组件放进对应 Story 节。

对每个 Story 展开：

### 4.1 实现设计

- 业务流程说明
- PlantUML 时序图或流程图（每图必释；颜色按附录 legend）
- 正常流程 / 异常流程 / 回滚 / 补偿流程
- 复用现有流程片段
- 新增 / 修改 / 删除范围

### 4.2 类 / 组件设计（OO 严格）

- 类 / 组件职责
- 类间关系
- 关键方法与输入输出
- 必要接口签名、前后条件、状态转换、不变量和依赖方向；同一对象在视图、接口和数据结构中使用同一身份
- 与现有命名和分层规范的一致性

按 [`abstraction-principles`](../../rules/abstraction-principles.md) 严格区分**对象 / 属性 / 动作**——禁动作当属性枚举、禁对象当属性枚举。

### 4.3 接口设计

- 逐项对应 §3.2 设计的用户动作、状态、成功与失败反馈；非页面场景对应真实调用方交互
- WebUI 接口 / 北向接口 / 内部接口
- 请求 / 响应结构
- 字段类型、必填/默认值、校验规则和失败返回；现役 schema/类型引用与本次变更映射
- 错误码
- 鉴权 / 审计 / 幂等 / 限流要求
- 兼容性策略

接口契约只给约定不给完整实现（实现归编码阶段）。

### 4.4 数据结构设计

- 数据库表 / 字段 / 索引 / 迁移
- 缓存结构与 Key 规则
- 配置项
- 文件 / 对象存储
- 数据生命周期与清理策略

## Step 5：可靠性、可用性、Function Safety 深度设计

写入 design.md §可靠性 / 可用性 / Function Safety 章节，按模板第 4 章处理：

- **软件功能流 FMEA**：故障模式 / 影响 / 检测 / 规避 / 恢复 / 改进措施
- **冗余设计**：组件冗余 / 数据同步 / 切换 / 脏数据处理 / 备份恢复
- **故障管理**：检测 / 隔离 / 定位 / 恢复 / 告警 / 日志 / 故障接口
- **过载控制**：检测点 / 限流点 / 默认阈值 / 丢弃策略 / 告警
- **升级不中断业务 / 前向兼容**：数据库 / 依赖 / 文件 / 包 / 预置数据 / 回退
- **人因差错**：高危操作确认 / 批量操作提示 / 审计 / 防误配置
- **故障预测预防**：KPI / 采集 / 统计 / 预测指标
- **公共系统依赖**：权限 / 告警 / 日志 / 证书 / 任务 / 备份恢复 / 资源管理 / 升级

每个小节必须写：涉及 / 不涉及、判断依据、设计措施、验证建议。不可简单留空。

## Step 6：安全、隐私、韧性深度设计

写入 design.md §安全 / 隐私 / 韧性章节，按模板第 5 章处理：

### 6.1 STRIDE 分析

- 2 层数据流图
- 数据流图元素表
- 业务场景及信任边界
- 外部交互方分析：S / R / P
- 数据流分析：T / I / D
- 处理过程分析：S / T / R / I / D / E
- 数据存储分析：T / R / I / D / P

每类威胁必给：威胁场景 / 现有控制 / 设计措施 / 残余风险 / 验证方式。

### 6.1.1 产品安全红线对照（🔴 设计期就评审，不等代码评审）

> 🔴 **安全在设计期就过红线，不留到代码评审**——设计阶段逐条对照[`产品安全红线`](../code-review/references/产品安全红线.md)（14 类 + 口令），在 design 里写明**本特性怎么满足相关红线**（不是事后补）。

- **A1 类零容忍**（后门 / 隐藏接口 / 硬编码口令 / 恶意软件 / 监听 / 隐私违规）——设计上**从源头杜绝**，design 里逐条说"不会出现 + 怎么保证"。
- **A2 类**（管理接口隔离 / 私有算法禁用 / 工作密钥不硬编码 / 凭据加密 / 审计日志不可删）——设计里给出对应机制。
- **B 类**（每个授权请求核权限 / 认证在服务端 / 无缺省弱口令 First login / 最小权限 / 敏感数据加解密）——设计里落到接口 / 数据 / 权限方案。
- 涉及的红线条目 → 进 design §安全章节逐条对照；**设计 Gate 评审时把红线对照作为必查项**（相关方签字含"红线已对照"）。

### 6.2 隐私风险分析

- 隐私风险预分析问卷
- 隐私风险预分析总结
- 个人数据列表
- 数据处理目的 / 处理方式 / 保护措施 / 留存期

不涉及个人数据 → 说明判断依据。

### 6.3 韧性设计

- 异常输入韧性
- 依赖服务不可用韧性
- 配置错误韧性
- 升级 / 回退韧性
- 资源不足韧性

写入 design.md §非功能性质量属性章节，按模板第 6 章处理：

- **可服务性**：日志 / 告警 / 诊断 / License / 运维效率

## Step 8：完整文档组装

按 Step 0.3 的资源合同做覆盖自检，**design.md 在 Step 0-7 边走边更新**。检查目录与适用完整段落、需求映射和未决项，再交实际评审/确认；未确认时保持 draft。设计成果交接时明确本次实际产出人与接收/验收人，Host 展示表单；人作出明确决定后调用 `add checkpoint`，也不从初始化配置推定签字。只有当前流程所需真实确认及证据齐备，才记录 implementable 和来源，不因文档已写完自动流转。

设计模板预置 `## 确认记录`。人对精确设计成果作出真实决定后，Host 才调用 `add checkpoint`；任一落点失败都不声称完成。完整语义由 Workflow 的“三处框架级软确认”统一定义，本 Skill 不复制第二套合同。

交评审前双向对账：每项已确认的边界与方案决定都能找到设计和验收落点；每个新增交互、接口或框架分支都能反查需求授权、方案依据及对旧消费者的影响。定点修复一处问题后仍检查受影响的全篇一致性，不把局部修复等同设计通过。

按模板章节组织：

- 文档头部：产品名称 / 密级 / 版本 / 拟制 / 评审 / 批准 / 关键词 / 摘要
- 缩略语清单
- 第 1 章：特性需求概述（IR / SR）
- 第 2 章：需求场景分析
- 第 3 章：特性 / 功能实现原理（**按端到端流程展开，不按子领域并列切片**）
- 第 4 章：可靠性 / 可用性 / Function Safety 设计
- 第 5 章：安全 / 隐私 / 韧性设计
- 第 6 章：非功能性质量属性相关设计
- 第 7 章：词汇表
- 第 8 章：其它说明
- 第 9 章：需求分解分配表
- 第 10 章：信息需求
- 第 11 章：参考资料清单

**自包含原则**：design 保留必要的设计结论、合同、依据和有效引用，不依赖将回收的步骤报告。取证日志不整批搬入；已有材料按实际用途、消费者、授权与保留约定交 [`knowledge-curate`](../knowledge-curate/SKILL.md) 处理，不预告全部删除。

**delta spec 同步 + 自动校验（收尾必做）**：

1. 项目已启用 change/spec 载体时，把本特性 BDD 场景 / 接口契约（Step 3-4 产出）按项目登记的路径和模板落为 delta spec。
2. 运行项目已登记的 schema/change 校验；校验不通过就当场修复。未启用该载体时，不生成空壳，不虚构命令。

## 沟通与默认推进规则

### 需要提问的场景

- 需求目标互相冲突
- 关键规格没有依据且会影响架构 / 资源 / 接口 / 兼容性
- 涉及安全 / 隐私 / License / 升级不中断 / 数据迁移 / 外部接口兼容
- 方案之间存在明显业务取舍

### 不需要等待确认的场景

- 过程文档落盘
- 低风险默认假设
- 代码搜索与模板读取
- 按模板补齐"不涉及"理由
- 将已确认信息同步到最终文档

### 默认推进记录

- 用户暂未回复时可继续无依赖部分；只有低风险可逆假设可标"默认采用"用于草稿，高影响未决项保持待确认，未确认不推进受影响实施
- **在 design.md 顶部 §决策追溯 §默认假设表追加一行**：ID / 假设内容 / 依据 / 影响章节 / 状态=默认采用
- 用户后续可拍板 → 状态改"已澄清"或"已修订"；不另开 logs/ 子目录

### ADR 引用规范（不复制内容，保 design 纯洁）🔒

**何时升 ADR**——决策同时满足：

1. **架构级**：影响微服务边界 / 跨服务接口契约 / 数据模型核心字段 / 错误处理基线策略
2. **跨特性**：决策结果会被多个特性 / 多个模块复用或受影响
3. **必含 alternatives**：候选方案 ≥2 + 现状/痛点/改造/效果四段论证

满足以上 → 走活动 3（adr-decision SKILL），落 `<decisions-dir>/<service>.md` 独立条目。

**design.md 引用方式**：

- frontmatter `related_adrs:` 列编号 + 一句话决策（不复制内容）
- 正文需要引用决策时，写"详见 ADR-NNNN（一句话决策）"，不复制 ADR 整段
- ADR 修订 → 检查实际消费者并同步 design 的受影响正文（对象、接口、数据、流程、验证）；ADR 的候选论证仍只保留原处。记录修订依据与未处理影响，不能仅改 `last_updated` 冒称同步完成。

**禁忌**：

- ❌ ADR 内容复制到 design.md 章节（违 SSOT，ADR 演进时两边不同步）
- ❌ design.md §默认假设把 ADR 级决策塞进去（升级不到位）
- ❌ feature-designer 自行写 ADR——必须走活动 3 + arch-designer + adr-decision SKILL

### improvements 多源写入规范（用户讨论后归集）🔒

`improvements/<service>.md` 是"已识别但本期不做的**重大优化项** backlog"——**3 个来源**，**共同准则：feature-designer / reviewer / arch-designer 不私自写入；都先抛主会话讨论，由用户拍"本期不做 + 归 improvements"才写入**。

🔴 **严重度门槛**——improvements 只收**重大优化项**（架构演进 / 跨服务影响 / 数据模型 / 工作量大）。**小点不进 improvements**：

| 性质 | 处置 |
|---|---|
| 小点（不动设计 / 不跨边界） | 在已有修改授权内交实施者修复，再独立复核；只做设计/评审时不自行改业务代码。引用 [`code-review`](../code-review/SKILL.md) 的 finding 闭环，不因“小”就扩权 |
| 重大优化项 | 跟主会话 / 用户对齐方案 → 拍"后续修"才写 improvements |

| 来源 | 触发活动 | 谁识别 | 谁写入 |
|---|---|---|---|
| 设计阶段识别 | 活动 5 详细设计 | feature-designer 主动 | 主会话讨论后写入 improvements + design §决策追溯 §improvements 引用表追加一行 |
| ADR 论证副产物 | 活动 3 ADR | arch-designer 在 alternatives 对比时识别 | 同上 |
| 评审 ISSUES 降级 | 活动 8 评审 | reviewer 标 `[重大-讨论]` + 主会话评估 | 用户讨论"本轮修 / 后续修 / 不修"——选"后续修"且确属重大优化项才写入 improvements + 关联 batch plan §变更记录；reviewer 标 `[现场修]` 的小点**不进** improvements |

**📂 improvements 文件归属判断**（按"改动落在哪个仓"归类；采用项目中的默认位置为 `.spec/improvements/README.md`）：

> 🚧 **待对齐**：本段为占位骨架，维度沿用框架（仓库 → improvements 文件映射）；具体值待 本项目 〈微服务划分〉拍板后填充（对齐项见 项目入口 §2）。

| 改动落点 | 归 |
|---|---|
| `<待填充:common-repo>`（SDK / 协议 / 公共接口；横切多服务 / 项目级亦公共归口此处） | `improvements/common.md` |
| `<service>` 各业务服务仓 | `improvements/<service>.md` |
| `<待填充:web-repo>` 前端 | `improvements/web.md` |

**default**：design.md frontmatter `related_improvements` 写完整跳转 `improvements/<service>.md#FI-NNNN`——不写 `<service>` 占位符；如归属不明先归 `common.md` 并在条目内注明"待跨服务讨论后可拆"。

**改 improvements 后必同步索引**：每条新增 → `improvements/README.md` 的索引表 + 文件组织段对应行追加 FI-NNNN。

**禁忌**：

- ❌ reviewer 自动把 ISSUES 转 improvements（必须用户拍板）
- ❌ 把 reviewer `[现场修]` 小点堆进 improvements（小点现场修——improvements 只收重大优化项）
- ❌ feature-designer 在 design §默认假设里塞"未来扩展点"（默认假设是本期推进；未来扩展归 improvements）
- ❌ improvements 写"必做项"（必做的归 task；improvements 是显式"暂不做"）
- ❌ design frontmatter `related_improvements` 留 `<service>` 占位符（必须填实际归属文件名 + FI 编号）

### 回复风格

- 简洁说明当前阶段、已保存文件、关键待确认问题
- 不在聊天中粘贴大段完整文档，除非用户明确要求

## 最终输出

完成后向用户输出：

- 工作区路径
- 关键过程产物路径
- 最终设计文档路径
- 高风险未确认项摘要
- 后续可继续调整的入口

## 与其他规则 / SKILL 的关系

- **前置**：[`boundary-grill`](../boundary-grill/SKILL.md)（5 段叙事 + 4 栏边界对齐）
- **写作准则**：[`design-doc-writing-style`](../../rules/design-doc-writing-style.md)（节首框问题 / 图后释 / 选型对比 / 措辞红线 / 性能数值占位 / 措辞统一）
- **OO 抽象**：[`abstraction-principles`](../../rules/abstraction-principles.md)（对象 / 属性 / 动作严格分离）
- **决策处理**：设计中遇决策点 → 引导到 ADR（[`decisions-guide`](../../rules/decisions-guide.md)）
- **后置**：向当前活动交回设计、实际确认状态、未决项和 Story 引用；已授权进入规划时由调用者交 [`task-decompose`](../task-decompose/SKILL.md)，再组织批次。单项设计授权不自动调用下一角色。
