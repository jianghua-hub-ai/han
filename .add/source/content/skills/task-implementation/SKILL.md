# Task Implementation — 单 Task 实施

## 何时启用

输入是批准设计下的可执行 task，或已确认预期行为与范围的授权局部变更时启用。存在批次才消费 `skill:batch-plan` 的批次合同；不要求每次小改都先建立批次或正式设计。设计决策、跨任务大重构和只读调研不使用本技能。

## 输入契约

| 字段 | 要求 |
|---|---|
| task / 变更 | 标识或当前请求引用、一句话可验证目标及修改授权 |
| 文件 | 新增/修改的精确文件清单与所有权 |
| 依据 | 批准的 design/ADR；或已确认预期行为、精确变更范围和真实消费者。不能两者都没有 |
| profile | 项目已启用且与本任务相关的实现 profile |
| 验收 | format/lint/type-check/build/test 或等价真实命令 |
| Git | 工作目录、分支、提交格式和禁止操作 |

缺任一关键字段时先补 Context Pack，不猜默认语言、路径或命令。

## Step 1：G0 必读

1. 复核影响面、消费者、公共契约和 project-local 差异；
2. 读取已存在且与本任务相关的需求/设计/ADR、指定 Rule 与启用的 profile；不预读无关流程库；
3. 基础设施/配置改动补齐真实读取者、默认策略和设计意图证据；
4. 在动手前汇报读取清单、适用约束、风险和停止条件。

既无批准设计也无已确认预期与范围，或影响面超出输入、结构决策未批准时停止。没有正式设计文件本身不是局部变更的阻断条件。

发现修复必须改变已确认的交互、API、框架接缝或其他消费者可见行为时，先按需读取 `rule:task-execution-workflow` §4.1，暂停受影响写入并交回变更依据；不把 task 授权推定为契约变更授权。

## Step 2：建立失败证据

- 新行为：先增加能表达期望的测试或等价可重复验证，使其在实现前失败；
- 缺陷：复用同版本、同环境下仍有效的复现、根因和 FAIL 证据；缺少证据才调用 `skill:systematic-debugging` Step 1–4 补证，不重复整套诊断与修复；
- 纯文档/配置：定义可机械核对的前后条件，避免无意义测试。

测试方法来自项目 profile；无专用 TDD 技能时执行 `rule:coding-standards` 的通用测试纪律。

## Step 3：最小实现

- 只改精确清单，匹配现有风格，不清理无关遗留；
- 遵守契约、配置、错误、资源、追踪和安全规则；
- 用最少实现让失败证据转绿，再在保持行为不变时整理自己的代码；
- 需要清单外文件、公共契约或设计变化时立即停手申请扩边界。

涉及前端页面时，将以下活动融入本步；非前端任务不加载这组材料：

- 页面或交互按以下顺序闭环：需求确认 → 设计确认 → 编码与自测 → 效果验收 → 评审/提交。
- 需求确认至少说明用户场景、页面用途、产品位置和功能范围；设计确认至少说明布局、交互、数据/API 和权限。未完成必要的人类确认，不开始编码。
- 效果验收必须让人看到实际交互或可复核的等价证据；只通过 type-check、lint 或 build 不算效果验收。
- 先核对当前用户操作、权限、数据与状态契约、异常路径及现有组件，再实现视图和事件；不先画页面再猜接口。
- 复用项目设计系统与状态管理约定，不默认绑定某个框架。落实适用的加载、空态、错误、权限、成功反馈、重试/取消与防重复提交。
- 对接真实 API 的字段和枚举；mock 与真实调用明确隔离，不用视图模型或旧 mock 结构冒充接口验证。

## Step 4：验证

按输入和启用 profile 运行真实命令：

1. 针对性测试；
2. 相关回归；
3. formatter/lint/type-check/build 等项目检查；
4. `git diff --check` 和敏感/调试残留检查；
5. 核对失败路径、行为证据和未自动化的人测项。

前端任务按适用场景自测关键操作、键盘/焦点、国际化、极端数据、重复提交与错误恢复；记录实际使用的客户端和路径。未验证的人工项明确交接，跨系统 E2E 不冒充开发自测。

命令失败时保留完整错误和当前工作树，先定位根因；禁止跳过、静默吞错或用较弱检查冒充。

## Step 5：提交前四项自验

1. `git status --short`：区分本 task 预期文件与已有他人改动；不要求整个共享工作树干净；
2. `git diff --stat`：规模与目标一致；
3. `git diff`：无无关改动，测试确实覆盖目标；
4. 仅在允许提交时暂存自己的精确文件，检查 staged 清单和 diff；已有无关暂存不混入本次提交。

不使用会带入无关文件的宽泛暂存方式。禁止提交时不为满足本步骤而暂存或提交。

## Step 6：提交与返回

- 允许提交时按 `skill:git-workflow` 创建可独立评审的提交，不 push；禁止提交或约定只交 diff 时，交付实际 diff 与验证结果，不虚报提交，也不把这类成功交付说成失败；
- 返回提交 SHA（如有）、文件清单、测试/检查结果、工作树状态、已知限制和人工验证项；
- Lead 必须在真实工作树复核状态、提交文件、diff 和验证，角色文本不能替代完成证明。
- 本技能完成表示实施证据已交付；待独立评审、复审或人工确认的任务不能据此直接关闭。持续记录和材料处置接回调用方 Workflow，不另建竞争台账。

## 失败模式

| 失败 | 处理 |
|---|---|
| 设计与代码冲突 | 停止，报告 design gap，不自行改设计 |
| 需要清单外文件 | 停止，说明原因和最小扩边界 |
| 检查命令不存在 | 核对启用 profile/项目入口，不自创默认命令 |
| 测试只在改后通过 | 说明为什么能证明回归，必要时补前置失败证据 |
| 工作树含他人改动 | 不还原、不覆盖，隔离自己的文件并报告冲突 |
| 需要真实跨系统验证 | 开独立 `skill:e2e-verification` task，不塞入开发 task |
