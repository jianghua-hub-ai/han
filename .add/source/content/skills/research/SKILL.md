# Research — 只读调研

## 何时启用

- 需要确认代码现状、消费者、跨模块依赖或历史原因。
- 需要比较业界方案、标准或当前版本能力。
- 设计、规划、评审前缺少事实证据。

不用于实现改动、替用户拍方向或生成长期过程文档。

## 输入契约

| 字段 | 要求 |
|---|---|
| 问题 | 一次调研只回答一个明确问题组 |
| 范围 | 仓库/模块/时间/版本/外部领域 |
| 排除项 | 明确不展开的相邻问题 |
| 证据标准 | 文件位置、提交、官方来源或数据 |
| 输出 | 期望表格、依赖图、对比或短报告 |

## 流程

### Step 1：冻结问题和边界

- 把问题改写为可被证据支持或否定的句子。
- 列出已知事实、待验证假设和停止条件。
- 识别是否需要当前版本信息；可能变化的事实必须查当前权威来源。

### Step 2：收集一手证据

优先级：真实代码/配置/测试与提交历史 → 项目设计/ADR → 官方规范和官方文档 → 可信二手资料。搜索摘要只用于找来源，不能单独支撑结论。

- 代码调研：找定义、读取者、写入者、调用方、测试和失败路径。
- 历史调研：找引入提交、相关决策、被替代方案和仍有效原因。
- 业界调研：先找标准/官方实现，再比较适配性、代价与失败模式。

### Step 3：交叉验证

- 至少用两个独立证据确认关键结论；只有一个证据时明确置信度。
- 文档与实现冲突时同时报告，不能默选其一为事实。
- 区分“设计了”“实现了”“启用了”“真实生效了”四种状态。

### Step 4：综合输出

按以下结构返回：

1. 结论摘要；
2. 证据表（结论 / 证据 / 状态 / 置信度）；
3. 冲突与未知项；
4. 风险和可选方向；
5. 建议的下一验证动作。

事实与推断必须显式标注。文件事实引用具体位置；外部事实链接直接来源。

## 失败模式

| 失败 | 处理 |
|---|---|
| 搜到配置就声称功能生效 | 继续找运行证据或标“仅配置存在” |
| 文档写了就当绝对事实 | 与代码、测试、运行状态交叉验证 |
| 用大量搜索结果代替结论 | 收敛到能直接支撑判断的一手证据 |
| 调研中顺手修复 | 停止，交 Lead 重新授权写任务 |
| 当前版本不可确认 | 报告版本边界，不用旧知识冒充当前事实 |

## 输出与清理

默认只在会话返回结构化摘要。只有输入明确指定永久产物时才写入项目知识目录；临时搜索结果不落 `.spec`。
