### B13J-D09-SEC-R01-F001 — `waived-for-test-scope` 语义不足，可能被下游当作 requires 已满足

- 级别：**MEDIUM**
- 位置：`.add/project/knowledge/decisions/framework.md:1216`（另见 `:1245`、`README.md:38`）
- 现状：r17 只写"该豁免只覆盖 S4.4 的模拟验证范围，不使 S4.5／S4.6 变为已实施，不改变其未派发状态，也不改变生产恢复链任何结论"。没有写明：该标签只对测试范围生效；不改变 `tasks.md:649` 所载 requires 的语义与 S4.5／S4.6 的生产要求；不构成安全豁免；任何下游不得把标签读成"requires 已满足"。
- 违反依据：ADR-0028 约束 3（不得伪造 PASS，`framework.md:849`）、约束 7（安全底线不变、不以"测试项目"豁免安全缺陷，`:853`）；ADR-0030 约束 5／7／9（`:1253`、`:1255`–`:1260`、`:1262`）。
- 触发场景：后续派发或关闭 S4.4、或以 S4.4 模拟结果承接 S2.2 时，执行者只读标签名或 README 摘要，未读到 `:1217` 的"卡面不放宽"句，就把 S4.5／S4.6 记为"已豁免"并作为 S4.4 依赖满足的证据。
- 影响：安全门禁的语义被稀释，标签可被引用为"依赖已满足"。因生产 `enter`／`install`／`resume`／`unlock` 仍 closed，暂不构成可利用缺陷；属安全结论可信度问题。
- 修复建议：在 `:1216` 或 `:1245` 固定一句："`waived-for-test-scope` 只对测试范围生效，不改变 `tasks.md:649` 的 requires 与 S4.5／S4.6 的生产要求，不构成任何安全豁免；下游卡面 requires、门禁、报告与 E2E 结论不得把该标签读作 requires 已满足，引用时必须同时引用本句。" 同时要求 S4.4 派发/证据记录指向 `framework.md:1216`，不修改卡面。
- 是否阻断：**是**（文档接收前必须修）。
- 复审条件：修订后文本包含上述四点；`waived-for-test-scope` 全仓语义一致；S4.4／S4.5／S4.6 卡面未改；修订后 `framework.md` 新哈希固定。

### B13J-D09-SEC-R01-F002 — S4.6 豁免归属与 ADR-0030 自述适用边界不一致

- 级别：**MEDIUM**
- 位置：`.add/project/knowledge/decisions/framework.md:1216`（对照 `:922`、`:1261`；消费者 `tasks.md:669`–`:687`）
- 现状：r17 把 `identity-auth-S4.6` 的依赖豁免记为"由本 ADR 作为**范围豁免**承接"。但 ADR-0030 继承关系 `:922` 明写"不改变 ADR-0019 已锁定的……key 轮换与退役"，约束 8 `:1261` 明写"本 ADR 不适用于……key retirement capability（ADR-0019 另定）"。r17 未说明该豁免只解除 S4.4 的派发依赖，不构成对 S4.6 生产合同或 ADR-0019 的任何解释、豁免或变更。
