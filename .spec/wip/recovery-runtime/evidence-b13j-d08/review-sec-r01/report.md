### `B13J-D08-SEC-R01-F001` — MEDIUM — 不阻断 r07 安全接受；阻断 S4.24a 在 r07 两路接受前的启动

- 位置：`tasks.md:3194`（S4.24a 硬 requires 段）、Plan `:1311` 与 `:1648`（B13J 批次门禁叙述）。
- 现文要点：`tasks.md:3194` 写「`identity-auth-D06` 已达决策接受级……故本卡启动门禁已解除」；Plan `:1311`/`:1648` 写「S4.24a 须 ADR-0031 r06 被接受（已于 2026-11-02 由两路 r02 接受……）」。
- 问题：ADR-0031 现行修订已是 `adr-0031-r07`，`:1129` 明确「r07 未获架构与安全两路接受前，`identity-auth-S4.24a` 及任何实施/验证卡不得启动（启动门禁回到 blocked）」。卡面与 Plan 仍以 r06 接受作为「门禁已解除」的依据，执行者按卡面而不是按 ADR 现状读取时，可能提前启动 S4.24a。这是规划制品的陈旧引用，不是 ADR-0031 文本缺陷。补充精度：Plan `:1648` 同段另含「D08（ADR-0031 r07 回填）已登记但未派发/未启动——r07 在审期间 `identity-auth-S4.24a` 暂缓启动」的缓解句，故残余误读主要集中在 `tasks.md:3194` 的「故本卡启动门禁已解除」；该缓解句不在卡面内，执行者只读卡面时仍会读到已解除。
- 攻击者/误用能力假设：无恶意攻击者；执行者在 r07 架构侧尚未接受时按卡面自述「门禁已解除」派发/认领 S4.24a。
- 要求动作：r07 两路接受后，由规划角色把 `tasks.md:3194` 与 Plan `:1311`/`:1648` 的 S4.24a 门禁引用从 r06 更新为 r07，并在卡面登记两路 r01 报告的路径 + SHA256 + verdict；在此之前不得以卡面文字主张启动。
- 是否阻断：不阻断 r07 的安全侧接受；阻断 S4.24a 的启动（ADR-0031 `:1129` 已独立生效，卡面须同步以消除误读）。

### `B13J-D08-SEC-R01-F002` — LOW — 不阻断

- 位置：`:1118`、`:1147`、`:1166`。
- 现文要点：回执抗伪造要求「读取时必须先验签」，同时允许「验证方式为外部系统验签，或由作为批准角色的人核对」。
- 问题：若实施方选择「外部见证」或「人核对」分支，文本没有定义与「验签」等价的完整性与真实性核验操作（见证端点身份、单调序列、审计字段），不同实现可能把「人看了一遍」当作「已验签」。这不构成决策级漏洞（合取与 fail-closed 仍在），但会给实现卡留下解释空间。
- 要求动作：在 S4.24a 的启动/关闭证据中定义见证分支的核验操作与审计字段（至少：见证端点身份、单调序列、读取时间、核验人/系统身份），或在下一次 ADR-0031 授权修订中把「验签」改为「验签或见证校验」并给出等价判据。
- 是否阻断：否；不影响 r07 安全接受。

### `B13J-D08-SEC-R01-F003` — LOW — 不阻断

- 位置：`:1117`、`:1144`（ENV denylist）、`:1134`/`:1141`（fd-exec 与批准二进制）。
- 现文要点：ENV 封闭字面集与 denylist 已覆盖环境变量注入；批准二进制要求 SHA256、`st_dev`/`st_ino`、受控只读挂载与固定 fd-exec。
- 问题：ENV denylist 不覆盖**文件型**动态加载注入面（如 `/etc/ld.so.preload`、`ld.so.cache`、RPATH/RUNPATH）。root 若可改写宿主加载器配置，获批二进制仍可能加载非批准代码。决策级的回执独立性与「root 可伪造即 closed」提供了兜底，但宿主隔离预检的取证清单尚未覆盖这一面。
- 要求动作：在 S4.24a 的宿主隔离预检/负向证据中增加加载器配置文件与 RPATH/RUNPATH 完整性核对（可优先静态链接或等价固定方式），并在关闭证据中登记；不要求本轮改 ADR。
- 是否阻断：否；不影响 r07 安全接受，但影响 S4.24a 关闭证据的完整性。

### `B13J-D08-SEC-R01-F004` — LOW — 不阻断

- 位置：`tasks.md:3136`（D08 卡验收命令第 2 条）。
- 现文要点：反向 oracle 写作 `rg -n '^\*\*修订\*\*: adr-0031-r06$' ... # exit 1`。
- 问题：ADR-0031 的修订字段与目的/仓库同处一行（`**目的**: 架构设计 | **仓库**: han | **修订**: adr-0031-r07`），行首不是 `**修订**`，该模式对任何修订号都永不匹配，`exit 1` 属空真（vacuous），不能证明「现行修订串不再是 r06」。同一卡 `:3135` 的正向 oracle 用 `^\*\*目的\*\*:.*修订\*\*: adr-0031-r07$`，是非空匹配；分段指纹又覆盖了其余禁改段，因此门禁实际仍有效，属证据质量问题而非安全缺口。
- 要求动作：把 `tasks.md:3136` 改为 `rg -n '^\*\*目的\*\*:.*修订\*\*: adr-0031-r06$' ... # exit 1`（与 `:3135` 同形），或改为显式计数判据（`adr-0031-r07` 在修订行恰 1 次、`adr-0031-r06` 仅出现在追溯行）。
- 是否阻断：否；不影响 r07 的安全侧接受，影响 D08 关闭证据中反向 oracle 的判定效力。

## 5. 启动门禁判定

- **`identity-auth-S4.24a`：安全侧判定为不可启动。** 理由：(1) 本报告只完成安全侧一半，9(b) 的双路合取还须架构侧对 r07 的独立结论由 Lead 合取确认；(2) `tasks.md:3194` 与 Plan `:1311`/`:1648` 仍以 r06 接受作为门禁依据，与 ADR-0031 `:1129` 的 r07 现行态不一致，须先由规划角色同步（F001）；(3) 即便两路接受，决策接受级也只解除派发/认领/开始改动限制，不补齐四项 unknown、不解除生产 closed、不产生人的批准。
- 四项 unknown（具名批准角色与两条批准记录、执行身份与切换机制、POSIX 隔离实测、产品级回执字段与真实样本）仍为 unknown；按三级门禁它们**不是**启动前置，但都是 S4.24a 的关闭证据。
- 生产 `enter`/`resume` 的 DB 替换继续 closed；「首期不提供生产 restore 工具与生产批准主体」不解除。
- 本评审不涉及 `identity-auth-S4.23`/`S4.24b`/`S4.22` 的门禁变化；它们各自的前置不受本报告影响。
