## 2. 核心问题逐条回答

### 2.1 (a) 形态级目标形态算不算「具体产品」？

**不算完整「具体产品」。**

`:951` 把候选 A 的「专用实例」子形态定为「独立 PostgreSQL 实例」，同时写明「具体大版本由部署方受支持版本清单在实施卡内固定，本 ADR 不写死版本」；`:947` 自述「本项是形态级建议值，不是产品选型完成」。PostgreSQL 是产品族，专用实例是部署形态，商业厂商、托管形态与大版本均未固定。

9(b)（`:975`）要求决策修订「给出**具体产品**、凭据来源、独立故障域论证、部署与 ACL 结论」。按字面，r05 只完成了产品族与部署形态，未完成「具体产品」。架构侧可以接受「PostgreSQL + 专用实例 + 明确排除同实例/共享备份链」作为**决策级目标形态**，但不能据此宣称 9(b) 的「具体产品」项已满足。

最小补法（二选一）：
1. 在决策层增加一条可核记录，固定厂商/托管形态/大版本（可由部署方支持清单派生，但必须由架构批准并留痕），再消费 9(b)；或
2. 明确修订 9(b) 的「具体产品」定义：产品族 + 部署形态即可，版本由实施卡第一步固定并回评审。该修订本身是 ADR 决策变更，须在 r05 或后续修订中明写，不能用解释性文字代替。

### 2.2 (b) 六项判据 + 四项否证条件是否构成「论证」？

**构成「可核判据」，但不构成完整的「独立故障域论证」。**

`:953` 给出六项判据（独立主机/集群与数据目录、独立存储卷与备份链、业务库 PITR/整库恢复不回退 anchor、独立网络入口与独立凭据、独立升级/维护窗口、演练证据）与四项否证条件（同实例不同 schema、同备份链、同超级用户、同维护窗口），并明确「本 ADR 只给判据与否证条件，不提供任何演练结果；真实验证属约束 7 与后续实施/验证卡」。

这与 9(b) 的「论证」/约束 7 的「真实验证」分层是自洽的：9(b) 不要求真实证据。但「判据」是**可测试的定义**，不是**针对本项目的论证**。当前缺两段推理：
1. 为什么「独立 PostgreSQL 实例」这一目标形态在给定部署拓扑下会满足六项判据；
2. 残余共享依赖分析：即使实例独立，云账号、区域、网络控制面、IAM/密钥管理、备份基础设施、监控与运维通道仍可能构成隐性共享故障域。

最小补法：增加一段「目标形态 → 六项判据」的推理与残余共享依赖清单；或明确把具体拓扑论证列为 S4.23 启动门禁的前置评审物（不是真实演练证据），并写清由谁在何时评审。

### 2.3 (c) 作者自评「9(b) 未满足」是否成立？

**成立，但理由需要更精确。**

作者报告 §10 的判断是「不能。本卡未满足 ADR-0030 约束 9(b)」，理由是本轮只交付形态级建议值与判据、未选定具体商业产品与大版本、且独立评审尚未发生。

我的独立判断：
- **决定性理由**是 9(b) 要求「架构**与安全**独立评审接受」。本轮只有架构侧评审（本报告），安全侧尚未发生；即使架构侧无条件接受，门禁也不能被宣称满足。
- **「具体产品」缺项**在字面读法下成立（见 2.1）。
- **「独立故障域论证」不足**在严格读法下成立（见 2.2），但比作者自述的理由更弱：判据 + 否证条件已构成论证的最低可核形态，缺的是项目特定推理与残余共享依赖分析。
- 作者说「独立评审尚未发生」在写作时点成立；现在架构侧评审已发生，但安全侧仍缺。因此结论仍成立，理由应更新为「安全侧未评审 + 产品/论证仍有缺项」，而不是笼统的「评审未发生」。

最少补什么才能满足：
1. 安全侧独立评审（必需）；
2. 产品厂商/托管形态/大版本的决策级记录，或 9(b) 定义的明确修订（见 2.1）；
3. 目标形态到六项判据的推理与残余共享依赖分析（见 2.2）；
4. 修复 `:958` 的启动条件矛盾（F001）。

### 2.4 (d) r04 表 A「不选」与 r05 把 A 的专用实例子形态定为后续目标形态，是否实质改写或自相矛盾？

**不构成实质改写，但存在可读性/自洽风险（F004，LOW）。**

`:947` 明确：r04 表中 A/B/C/D 的「不选/选定」记录的是 2026-11-01 时点「是否现在选定并交付」的判断，历史结论不改写；r05 只把候选 A 的专用实例子形态定为后续实施的目标形态，B、C 仍不选，首期仍不交付。`:936` 的 A 行「不选」未被改写；`:939` 的 D「选定」未被改写；「首期不提供」标题与 `:926` 决策未变；A 的「独立 schema」子形态仍被 `:951` 排除。

因此，决策结论（首期不提供、D 选定）没有实质改写；变化是**在未来选项空间内把 A 的专用实例子形态标为目标形态**，并显式标注为「Lead 采纳的建议值」。这属于决策级建议，不是生产选型完成。

风险在于：`:936` 的「结论」列仍写「不选」，而解释在 11 行之后的 `:947`；只读候选表的读者可能把「不选」理解为永久排除。建议在 A 行加指向 `:947` 的脚注或在表下加一句「不选＝当前不选定并交付，非永久排除；后续目标形态见 r05 (a)」。

### 2.5 (e) 把四项登记为「Lead 采纳的建议值」是否越界？

**未越界。**

`:920`、`:947`、`:987` 均明确：2026-11-02 的 standing 授权只是流程推进，不构成人的成果接收、独立评审、生产装配批准或真实验证；四项是「Lead 采纳的建议值」，不是「用户已确认」「已验证」「已批准」；`:958` 明确「并未满足该门禁」「不得以本段措辞冒充已论证或已满足」。

因此，登记没有把建议值写成人的成果接收、生产批准或已验证。需要保持的边界是：「Lead 采纳」不得被下游读者等同于「架构与安全独立评审接受」；`:958` 已作此限定，建议在后续引用时继续保留该限定。

## 4. S4.23 启动门禁判定

**不满足。**
