## 5. 三问回答

### Q1 — CLOSED

r07 后 `(a)(b)(c)` 与 `:983`–`:992` 已收敛为唯一权限矩阵：

- 头事件表只有 `SELECT`/`INSERT`；
- 无 `UPDATE`、`DELETE`、`TRUNCATE`、DDL、跨库与超级用户；
- CAS 语义为 `(namespace, revision)` 唯一约束上的 `INSERT` 冲突；
- head 由已提交事件派生，不做事务内原地状态转换。

「是否仍有可被读成需要 `UPDATE` 权限的残留表述」：没有。r06 及更早的追溯行（`:1030`）只保留了「或等价外部见证」的历史措辞，已被 `:983` 作废；r05 表头「建议值」是强度标签，不是权限语句。历史字面保留属追溯，不构成现行规范，判为可接受。

需要说明的是：权限矩阵唯一，不等于写入模型已可实施——CAS 键与 pending/committed 的关系仍不成立，见 R03-F002（新问题，不由 Q1 承担）。

### Q2 — NOT CLOSED（本轮核心）

**攻击者能力假设**：控制 anchor 实例、其备份与恢复（恶意或被攻陷的 anchor 管理员、或同一 DBA），不持有见证写凭据（`:989`），可读 ADR 与部署配置，可在任意时刻终止进程或阻断见证端点。该能力假设与 `:977` 的否证条件一致（同一 DBA 可在同一窗口回退业务库并改回 anchor 头即否证），因此它就是 ADR 自认在模型内的对手。

**攻击链**（逐步都符合 r07 现行文本）：

1. 正常提交 revision N：事件行 `INSERT` 成功。`:991` 允许「提交事件后同步推进见证」，于是存在一个窗口：head = N、见证 = N−1。
2. 让见证推进失败（阻断网络、拒绝写）或在推进前 `kill -9`。`:992` 要求「见证不可写 → closed」，服务停止；但状态留在 head = N、见证 = N−1，而这是「已声明滞后」的**合法**组合。
3. 用一份在 revision N−1 提交后、N 提交前取得的备份做整实例回退。回退后 head = N−1、见证 = N−1（见证在域外，不被回退）。
4. 重启：`:990`/`:992` 的判据是「见证低于 head 即 closed」。此时见证 == head，判据不触发；「至多 1 个 revision 的检测滞后」也已由部署方写入批准记录。
5. 以不同 payload 重新占用 revision N：回退后该键为空，`(namespace, N)` 的 `INSERT` 不冲突，CAS 成功。一个已向调用方确认的提交被静默抹去，已消费的 run 可以在 anchor 侧重新落成。

**为什么这不是「概率极小的崩溃窗口」**：

- 滞后分支把「见证 < head」定义为合法状态，而回退能产生的最自然结果正是「head 被降到见证」。二者观测等价。
- `:991` 只说「同步推进」，没有定义同步点（同一事务？进程返回前？第二次网络写？）。实施者可以合法地实现为「先返回成功、后台再推进」，窗口就从毫秒级崩溃窗口变成任意长度。
- `:992` 的「见证不可写 → closed」并不安全：该 closed 状态留下的组合（head = N、见证 = N−1）恰好能被第 3 步的回退「治愈」，故障分类本身成了不在场证明。

**「先预留见证、后提交事件」分支评估**：该方向是安全的。回退后见证 ≥ N+1 > head，必然触发 closed。代价是崩溃会烧掉预留的 revision（可用性与容量问题，不是回退检测空档），但前提是预留必须带 writer token，使被预留的 revision 只能由同一操作消费；否则不同 payload 可以占用同一预留位。

**「见证高于 head 属已声明预留」评估**：不构成空档。攻击者无法把 head 抬到见证以上（那需要一次成功提交），只能把 head 降到见证；而降到的位置若低于当前见证就必然触发 closed。

**可执行改法**（择一或并用）：

1. 取消滞后分支：只允许「先预留见证、后提交事件」，并要求见证值在任何时刻 ≥ 已向调用方确认的最大 revision；预留带 writer token，废弃预留以追加 `abandoned` 事件收尾，不得把该 revision 复用给不同 payload。
2. 若保留「提交后推进」，则把「提交成功」定义为「事件 `INSERT` 与见证持久推进到 ≥ N 都完成」，即见证推进先于向调用方返回成功；启动或任何推进前若观测到见证 < head，一律 closed 且**不得自愈**（不得用观测到的 head 直接抬高见证），只能凭带外回执（例如 Journal 已确认 head 加具名运维处置记录）解除。
3. 明确见证值的语义：等于「已提交事件的最大 revision」，不把 pending 计入；pending 造成的预留另用预留记录表达，否则「清除未发布 pending」会让见证永久高于 head。

**blocking**：是。

## 6. 新 findings

### B13J-D05-SEC-R03-F001 — HIGH — 「至多 1 个 revision 检测滞后」使整实例回退不可检测

- **位置**：`framework.md:991`；关联 `:953`、`:990`、`:992`、`:970(ii)`
- **现文要点**：只允许两种写入次序，「先预留见证、后提交事件」（见证高于 head 属已声明预留），或「提交事件后同步推进见证并声明至多 1 个 revision 的检测滞后」；未声明滞后而见证低于 head 即 closed。
- **问题**：见 Q2 攻击链。核心是「声明滞后」把「见证 < head」变成合法稳态，使「head 被回退到见证」这一回退结果不可观测；且「同步推进」未定义同步点，窗口可被拉长到任意长度；`:992` 的 closed 状态可被一次 anchor 回退「治愈」。攻击者无需任何超级用户或见证写权限，只需 anchor 备份/恢复权与一次进程终止。
- **可执行改法**：删除滞后分支，或把「见证 ≥ 已确认 head」设为向调用方返回成功之前的硬前提；启动时观测到见证 < head 一律 closed 且不得用观测 head 自愈；预留分支补 writer token 与 `abandoned` 收尾；在 `:953`、`:967`、`:991` 三处同步措辞。
- **blocking**：是。关闭条件：上述三处一致，且文本中不再存在「见证 < head 可合法持续」的读法。

### B13J-D05-SEC-R03-F002 — HIGH — `(namespace, revision)` 唯一约束与 pending/committed 双事件不可共存，并与 ADR-0019 两段 CAS 冲突

- **位置**：`framework.md:951`、`:983`、`:985`；上游硬边界 `:451`、`:467`、`:468`（ADR-0019），约束 1 见 `:1004`
- **现文要点**：单一 append-only 头事件表，`(namespace, revision)` 唯一约束承担 CAS，pending 与 committed 各为事件类型，不做事务内原地状态转换，head 由已提交事件派生，应用角色仅 `SELECT`/`INSERT`。
- **问题**：
  1. 同一 revision 若要同时存在 pending 与 committed 两行，`(namespace, revision)` 唯一约束必然拒绝第二行；若把 kind 并入键，则 committed 行与 pending 行之间没有任何约束绑定，任何持有该角色的写入者（输掉 pending 竞争的实例、被复用的连接池、或以应用角色临时连接的 anchor 管理员）都可以跳过 pending 直接 `INSERT` committed，派生 head 随之前进到一个从未被预留的 revision。
  2. ADR-0019 `:451` 要求「以 expected revision 对 next committed/pending 状态执行 compare-and-swap」，`:467` 要求「CAS 从旧 committed 头进入 pending 新头 → … → CAS pending 为 committed 新头」，`:468` 要求崩溃恢复时「清除未发布 pending」。这三条描述同一 head 记录的状态迁移；r07 的「不做原地状态转换、无 DELETE」既未给出等价映射，也未说明「清除」如何用 `INSERT` 表达，而约束 1 把该 CAS 协议列为硬边界。
  3. 攻击者能力假设：持有 anchor 应用凭据的竞态写入者，仅用合法 `INSERT` 即可把 head 推到自选 revision，无需超级用户。
- **可执行改法**：
  - 事件表键改为 `UNIQUE (namespace, revision, kind)`，committed 行携带写入者在插 pending 时生成的不可预测 `pending_token`，并建外键/部分唯一约束使其只能引用匹配的 pending 行；该约束由部署方一次性脚本创建，运行时不需 DDL。
  - 把 ADR-0019 `:468` 的「清除未发布 pending」映射为追加 `abandoned` 事件（head 派生忽略 abandoned），并在 ADR-0030 写明该映射与三态恢复判定。
  - 补负向测试：两个写入者并发插同一 revision 的 pending，恰好一个成功；失败者不能插 committed；无 token 或 token 不匹配的 committed 必须失败。
- **blocking**：是。关闭条件：唯一键、pending→committed 表达、abandoned 映射与 ADR-0019 三态恢复一一对齐，且负向测试可失败。

### B13J-D05-SEC-R03-F003 — HIGH — 域外见证的形态与保证等级未定，且未进入 `:958` 缺项清单

- **位置**：`framework.md:988`、`:953`、`:958`
- **现文要点**：见证「具体形态（例如域外单调计数器、WORM 或审计存储等）由部署方在受支持清单内固定并写入 (b)(d) 的批准记录，本 ADR 不选定产品、不写死形态」。
- **问题**：见证是 r07 之后唯一抵抗整实例回退的机制，把其形态与保证等级整体外推，等于把 9(b) 要求的安全结论交给实施期。若部署方选了可被同一备份链回退、或支持递减/重置的见证，anchor 管理员只需把两侧回退到同一时点即可绕过全部检测，而文本不会阻止。`:958` 的缺项只有产品、版本、许可与 owner、目标环境，缺少见证，导致该缺口在门禁上不可见。攻击者能力假设同上（anchor 备份/恢复权，无见证写权）。
- **可执行改法**：在 `:988`/`:953` 增加见证的保证等级（不指定产品）：单调（无角色可递减、无重置接口）、持久（确认写跨 anchor 故障域存活）、不可被 anchor 管理员经备份/快照恢复降低（或 WORM/对象锁保留期 ≥ anchor 备份保留期）、可审计（每次推进留可核记录）；把「见证形态、owner 与保证等级取证」补入 `:958` 的 (i)–(iv) 或新增 (v)；在 (c) 否证条件加「见证可被 anchor 管理员经任一备份/恢复路径降低 → closed」。
- **blocking**：是。

### B13J-D05-SEC-R03-F004 — HIGH — 见证的端点与写入凭据未落进现有配置/凭据合同

- **位置**：`framework.md:952`、`:1006`（约束 3）、`:989`；下游 `tasks.md:3096`–`:3101`、`:3120`
- **现文要点**：生产只认 `HAN_RECOVERY_ANCHOR_ADAPTER` 与 `HAN_RECOVERY_ANCHOR_CONFIG_PATH`；配置文件只承载非秘密连接字段；口令只经一次性 fd/stdin；见证写凭据须与 anchor 凭据分属不同保管主体。
- **问题**：r07 之后 adapter 必须同时连 anchor 与见证，即需要两个端点与两个秘密。现行文本没有给出：见证端点的承载位置（配置文件新段？新键？）、第二个秘密的注入通道与次序、两个秘密同时进入同一进程的边界。可预期的后果是三选一——把见证口令写进配置文件（违反「只承载非秘密字段」）、新增第三个环境键（违反约束 3 的「生产只认」）、或复用同一 fd 通道而无法体现不同保管主体。已登记的 S4.23 卡写集 4 文件不含任何见证实现，其停止条件（`tasks.md:3120`）又明写「若需新增配置键……停止并回设计」，照现状推进只会触发停止条件或诱导违规实现。攻击者能力假设：能读配置文件或进程环境的低权本机用户；一旦见证口令落盘/落环境，「分属不同保管主体」即名存实亡。
- **可执行改法**：在 (b)/(d) 明确：配置文件允许一个 `witness` 段，只含非秘密字段（端点、来源地址、TLS CA/主机名）；见证口令经**第二次**一次性 fd/stdin 注入，注入者与保管主体在批准记录中不同于 anchor 口令；配置文件出现任何秘密字段即 closed；见证写入的 TLS/超时/失败分类与 `:992` 对齐。若确需第三个配置键，属约束 3 正文变更，必须走 ADR 修订，不得由实施者在卡内决定。
- **blocking**：是。

### B13J-D05-SEC-R03-F005 — MEDIUM — 「分属不同保管主体」不可核验，且「批准记录」无定义

- **位置**：`framework.md:953`、`:989`、`:988`；否证条件 `:977`
- **现文要点**：见证写入凭据与 anchor 连接凭据必须分属不同保管主体，复用即否证；运维责任（含见证）未落到具名部署角色时装配即 closed。
- **问题**：纯文字约束，无取证方式；「写入 (b)(d) 的批准记录」中的批准记录在 ADR-0030 内没有字段、位置与签署者定义，无法判断是否落过。adapter 运行时必然同时持有两个凭据，该分离只对签发/轮换/读取成立，对宿主攻陷不成立，而 ADR 未声明威胁模型边界。攻击者能力假设：单一 DBA 或单一秘密库管理员，能同时签发两侧凭据，或把两者放进同一 Vault 路径。
- **可执行改法**：在 (d) 或 `:989` 定义批准记录最小字段（两个具名保管主体、两个秘密存储位置、轮换窗口是否可合并），并加否证条件「同一秘密存储/同一账号可读两侧/同一变更窗口可同时轮换 → closed」；在 r07 补充段写一句威胁模型边界。
- **blocking**：否（须在 S4.23 启动前落到批准记录，见第 7 节门禁 6）。

### B13J-D05-SEC-R03-F006 — MEDIUM — 整实例回退演练未覆盖「回退到与见证相等的备份」

- **位置**：`framework.md:970(ii)`、`:994`
- **现文要点**：anchor 实例整体回退到旧备份并重启后，下一次 CAS 必须失败；判据只来自域外见证。
- **问题**：「旧备份」未定义边界。按滞后分支，回退到「head 恰等于见证」的备份时下一次 CAS 会成功，而演练清单不要求覆盖这一档，于是演练可通过而缺陷仍在。此外「下一次 CAS 必须失败」弱于 ADR-0019 的 fail-closed：判据应是「在任何 enter/install 之前即 closed，且无 anchor 写入」。
- **可执行改法**：演练集固定四档——(A) 与当前见证相等的备份（对照，判为无回退）；(B) 恰为见证 − 1 的备份（滞后边界，必须 closed）；(C) 更旧备份（必须 closed）；(D) 新副本冷启动读到 head < 见证（必须 closed）。判据改为「服务任何 enter/install 之前 closed 且无 anchor 写」，并要求重启后首次核对不使用进程内缓存。
- **blocking**：否（验证卡阶段必须执行，见第 7 节门禁 3）。

### B13J-D05-SEC-R03-F007 — LOW — 「或等价受控通道」是未定义的旁路措辞

- **位置**：`framework.md:952`
- **现文要点**：口令只经一次性 fd/stdin 或等价受控通道注入，禁止经 environ 继承……
- **问题**：同句后半段禁止 environ/argv/配置文件明文，前半段却留「等价受控通道」。实施者可据此把口令写进临时文件或第三方工具的本地缓存，绕开一次性 fd/stdin 语义。攻击者能力假设：能读本机临时目录或进程环境的低权用户。
- **可执行改法**：删除「或等价受控通道」，或限定为「不得落入文件系统、environ、argv、日志、Trace 或任何可被非保管主体读取的介质」。
- **blocking**：否。

### B13J-D05-SEC-R03-F008 — LOW — (b)–(d) 仍以「建议值」命名，与「要求」强度不一致

- **位置**：`framework.md:945`、`:947`、`:949`
