## 3 必答问题逐项

### Q1 约束 2 的「SQL」限定是否被安全地收窄

现文 `:1042` 由五句构成：禁止以 file、SQL、业务 PostgreSQL 表、内存、fake 或「环境探测后自动选择」填补生产 anchor；**「SQL」仅指以业务数据库或通用 SQL 表作为 anchor 的自动 fallback 或隐式来源**；显式登记、显式配置、固定指向独立故障域实例的 adapter 不属于被禁路径；不得把测试替身注册为生产 provider；不得以空 registry 之外的方式隐式构造 adapter。

**判断：可接受，且不构成绕过「无 fallback」的口子。** 理由：

- 收窄的是**名词外延**（「SQL」= 业务库自动 fallback/隐式来源），不是**行为豁免**；「不得环境探测后自动选择」「不得测试替身注册为生产 provider」「不得隐式构造 adapter」三句原样保留，运行期自动选择与隐式默认仍被禁。
- 被放行的形态要求同时满足「显式登记 + 显式配置 + 固定指向独立故障域实例」三个合取前提；这与 ADR-0019 的独占锚点语义、ADR-0030 `:953(c)` 六项独立故障域判据、ADR-0032 不变量 7（`:1205`「不改变既有决定与合同」）方向一致，而不是替换它们。
- 未引入 file / 内存 / fake / 环境探测路径；未放宽「首期不提供」结论与生产 `enter`/`install` closed。

残余风险（非阻断，但必须由实施卡取证，已列为条件 C2）：三个前提都是**事实性前提**，ADR 不取证。若 S4.23 以「已显式登记」为由把 adapter 指向业务库同实例或同备份链，则字面不违反约束 2，但仍被 `:953(c)` 否证。因此安全侧要求 S4.23 的退出条件必须包含「独立故障域六项」的取证，而不只是「配置显式」。

### Q2 `Exclusive` 从 S4.23 移到 S4.24b 是否削弱 fail-closed

现文：`:1218` 条件 8 规定条件 1–7 任一未满足即不得解除；`:1220` 候选 S4.23 只把 `Exclusive` 作为「已登记但 closed 的端口接入 bundle，不得填实现、不得脱离 closed 端口状态」；`:1222` 候选 S4.24b `requires` 候选 S4.23，「bundle 必须先于锁后端接线，不得先接线后补来源」，「`Exclusive` 离开 `recoveryClosedPort` 由本节点交付完成」；`:1226` 给出无环论证。

不变量与解除条件 1–7 未变：`:1199` POSIX-only + 任何状态变更前退出码 2 + 无 fallback/降级；`:1200` 三入口（`normal`/`recovery`/`requeue`）共用同一锁路径与持有期且覆盖整个 runtime 生命周期；`:1211` `O_CLOEXEC` 常驻 fd；`:1213` 四类负向测试；`:1216` 人的明确生产批准不可被 Agent 产出替代；`:1217` Windows 生产须另立 ADR。

**判断：不削弱 fail-closed，反而更严。** 原口径下 S4.23 单卡即可把 `Exclusive` 带出 closed 并同时交付 CAS 头；现口径要求 bundle 先交付、再由受同一门禁的后继卡带出，且卡面 `:3222` 明令「不得先接线后补来源」。路径/ACL、`journalPath != lockPath`、退出码 2、`O_CLOEXEC`、三入口共锁均在未改动的条件 1–7 与卡面 `:3218(2)(3)(6)` 中保留。
