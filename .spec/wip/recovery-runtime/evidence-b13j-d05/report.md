## 3. 四项结论（逐项）

结论载体：`framework.md:944-958`（`#### r05 四项结论（决策级建议值；不构成交付、装配或验证）`）。四项均为**决策级建议值**，依据用户 2026-11-02 standing 授权「对待确认或决策项采用建议值并继续本项目」登记为 Lead 采纳的建议值；该授权是流程推进，不构成人的成果接收、独立评审、生产装配批准或真实验证。

### (a) 产品与部署形态

- 结论：候选 A 的「专用实例」子形态——独立 PostgreSQL 实例（独立集群与数据目录、独立主机或独立实例加独立存储卷、独立网络入口）承载单表 CAS 头状态（`journal_id/namespace/epoch/head_sequence/head_hash/revision`）；唯一 adapter 按 namespace 读快照与 revision，以 expected revision 条件 `UPDATE` 实现 CAS，pending/committed 在事务内转换；具体大版本由部署方受支持版本清单在实施卡内固定，本 ADR 不写死版本。
- 理由：关系型条件写是成熟 CAS 语义；独立实例是唯一能在不引入新协议的前提下同时满足「独立故障域」与「不随业务 PostgreSQL 回退」的形态；不引入 file/SQL/fake 任一被禁路径。
- 排除的替代路径：业务库内独立 schema、同实例另一库、共用备份链（都会随同一故障域回退）；候选 B（Vault/KMS）与 C（对象存储条件写）维持 r04 的不选；file、业务库表、内存、fake 恒禁。
- 失败或降级条件：只能提供同实例或共享备份链时，本项降级为「首期不提供」，生产继续 closed，回到用户做产品与环境决策。
- 未验证边界：未选定商业产品、许可、大版本、托管形态；未取得实例、凭据、ACL、拓扑或任何演练证据。本项是**形态级**建议值，不是产品选型完成。

### (b) 凭据来源与最小权限 / ACL

- 结论：专用数据库角色，仅该实例该库锚点表的 `SELECT`/`INSERT`/`UPDATE`，无 DDL、`DELETE`、`TRUNCATE`、跨库与超级用户；口令只经部署方的秘密注入通道进入进程，不进 argv、日志、Trace 或仓库；`HAN_RECOVERY_ANCHOR_CONFIG_PATH` 只承载非秘密连接字段，必须绝对路径、owner-only、no-follow；建表与 GRANT 由部署方一次性受控脚本完成，运行时不持 DDL 权限；连接限定来源地址并启用 TLS。
- 理由：把「能 CAS」与「能改结构/删数据」分开，使误用与凭据泄露的爆炸半径限于单表读写；ACL 与 GRANT 由部署方在带外固定，本服务不持 DDL 是 fail-closed 的最小集。
- 排除的替代路径：复用业务库角色、以超级用户运行、把口令写入配置文件或命令行、运行期持有 DDL。
- 失败或降级条件：角色与 GRANT 矩阵未取证、配置路径可被非 owner 读取、或口令出现在 argv/日志时一律 closed。本 ADR 不登记任何角色名、主机名或秘密值。
- 未验证边界：无角色、无 GRANT 实测，无口令注入通道实现，无 ACL 取证。

### (c) 与业务 PostgreSQL 独立故障域的可核论证

- 结论：给出六项可核判据——(1) 独立主机/集群与数据目录；(2) 独立存储卷与备份链；(3) 业务库 PITR 与整库恢复不回退 anchor；(4) 独立网络入口与独立凭据；(5) 独立升级/维护窗口；(6) 演练证据（业务库回退到旧快照后 anchor 仍拒绝已消费 run 与旧头）。
- 理由：ADR-0019 要求 anchor 独立故障域且不随 PostgreSQL 回退。仅「不同 schema/不同库」在备份、PITR、维护窗口与凭据上仍同域，故必须用可观测、可演练的判据而非部署措辞来判定。
- 否证条件（出现任一即不成立）：同实例不同 schema、同备份链、同超级用户、同维护窗口。
- 失败或降级条件：六项判据任一无法取证即不成立，本项降级为「首期不提供」。
- 未验证边界：**本 ADR 只给判据与否证条件，不提供任何演练结果**；真实验证属 ADR-0030 约束 7 与后续实施/验证卡。

### (d) 部署拓扑与运维责任

- 结论：部署方拥有实例、备份/恢复、凭据轮换、ACL 复核与演练并保留证据；本服务只经 adapter 读写，不迁移、不建表、不做备份；业务 PostgreSQL 与 anchor PostgreSQL 分属不同故障域，两库之间无事务、无复制、无共享凭据。
- 理由：把「谁对可用性与证据负责」写清，避免恢复链把未定义的运维责任隐式转嫁给应用；也与「不随 PostgreSQL 回退」的技术判据配套。
- 排除的替代路径：由本服务托管 anchor 实例、由应用迁移建表、与服务共用 DSN。
- 失败或降级条件：运维责任未落到具名部署角色时，装配即 closed。
- 未验证边界：未指定任何部署方角色名、组织或 SLA；未做责任交接。

## 4. 为什么没有把四项全部写成「首期不提供」，以及仍然缺什么

- ADR-0030 的结论**没有变**：仍是「首期不提供生产 CAS JournalHeadAnchor provider」，S4.5 维持未交付，生产 recovery `enter`/`install` 继续 closed。r05 只补齐「本 ADR 尚无产品/凭据/独立故障域/部署与 ACL 结论」这一文档缺口。
- 能从现有事实推导的部分：ADR-0019 已固定 CAS 语义与故障域要求，design 已固定两个配置键与「未配置即 closed」，因此「专用 PostgreSQL 实例 + 专用最小权限角色 + 六项故障域判据 + 部署方担责」这一形态可以从既有约束推导为**决策级**目标形态，不必虚构外部产品事实。
- 仍然缺、且不能靠文档补齐的部分：具体商业产品与许可、受支持大版本、真实实例与网络拓扑、真实角色/GRANT/ACL 取证、真实独立备份链、演练证据。**因此严格意义上「给出具体产品」这一项仍未完成**——本轮给出的是形态级建议值，不是产品选型完成。评审若按 ADR-0030 约束 9(b) 的「具体产品」字面判定，应判该门禁**未满足**。
- 未采用的替代做法（并说明为何不采用）：(i) 直接写某个云厂商托管 PostgreSQL 具体型号——无证据支撑，等于把未验证写成已决定，禁止；(ii) 四项全部写「首期不提供」——会掩盖已可从既有约束推导的形态结论，也无法为后续评审提供任何可评审对象；本轮选择「形态级建议值 + 明确的降级条件 + 明确的门禁未满足声明」。

### 18.4 本轮修正的两处自身缺陷

1. **`reserved_head` 与「最大已占用 revision + 1」互斥**：首稿 r08 同时写「`reserved_head` 为最大已占用 revision + 1」与「`reserved_head == last_confirmed_head + 1`」，在存在 abandoned 或 pending 时两者给出不同值。已统一为单一状态机（`:990`、`:1007`）：CAS 预留值只由已结算水位推进，事件表 `MAX(revision)` 仅用于判定占用，不作预留值来源。
2. **abandoned 稳态下演练 (D) 会误判**：若以「head」泛指已结算事件最大 revision，则最近一次结算为 abandoned 时 `head = last_confirmed_head`，与见证相等，演练 (D) 将无法触发。已把 (D) 与 `:953`/`:967` 的比较对象改写为「anchor 观测水位（已结算事件的最大 revision）」并补「`head ∈ {last_confirmed_head − 1, last_confirmed_head}` 且差 1 必须有 abandoned 行」。
