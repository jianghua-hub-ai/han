## 3. 逐条结论

### 3.1 RV-01 是否真关闭 —— **CLOSED**（附 RV2-02 注记）

- **(a) 写入侧否定：具备。** `:3862` 现含“只允许对目标 DB 执行 restore 与只读验证，不得写 Journal/keyring、部署锁、Store 绑定或审计，不得自行建立权威 binding”。
- **(b) 可核验强制机制：具备。** `:3862` 现含“其目标连接凭据必须属于独立数据库角色，该角色权限不得覆盖 identity/recovery 表写入，数据库角色与 GRANT 矩阵由批准记录固定、未证明即保持 closed”；ADR 侧新增 `:1036` 负向验证门禁。机制本身留解除条件实测，符合要求。
- **(c) 追溯句：基本一致。** `:1045` 列举的落点均可在 `:3862` 原文逐字找到（保留部署锁/Journal/keyring/Store 绑定与审计写入的权限边界、执行身份不得写、独立数据库角色 + GRANT 矩阵、除目标连接外无网络、禁止 su/sudo/shell 脚本包装），不再把 `:3862` 未写的内容算作“已固定”。唯一不准是“进程组/no-follow”术语归属 → `B13J-D03-RV2-02`（LOW，不阻断）。

结论：三项判据均不再缺失，原 finding 的技术内容关闭。但 (b) 引入的机制措辞自带新问题，见 3.6。

### 3.2 RV-02 是否真关闭 —— **CLOSED**

- (a) 供应方自批：`:3862` “批准者不得同时是执行者、本次 run 发起者或工具/备份供应方自批”。
- (b) root 不代替执行 / 不进 shell / 不重放：`:3862` 同句列举。
- (c) 无网络出口：`:3862` “执行身份除目标 DB 连接外无网络出口”；ADR `:1035` 同义。

### 3.3 RV-03 是否真关闭 —— **CLOSED**

`framework.md:981` 现写“与 ADR-0030 的合并口径是‘生产 `enter`/`install` 与 `enter`/`resume` 的 DB 替换路径均保持 closed’，二者是不同入口而非范围收窄”。ADR-0030 `:926` 原文“生产 recovery `enter`/`install` 继续返回 closed”未被改动（前缀哈希覆盖），且 ADR-0031 `:977`/`:1024` 明示不改 ADR-0030，净效果仍全闭。

残余措辞风险（不阻断）：把“DB 替换路径”同时挂到 enter/install 上，单读 `:981` 可能被理解为 ADR-0030 的 closed 仅限替换路径；建议后续改为“enter/install（ADR-0030）与 enter/resume 的 DB 替换（ADR-0031）各自 closed”。

### 3.4 RV-05 是否真关闭 —— **CLOSED**

`:1006` 与 `:3862` 都明确禁止“经 shell 脚本、`su`、`sudo` 等包装实现”，且均未把机制写成已选定：ADR 写“具体切换机制由批准记录固定…本 ADR 不选具体机制”，design 写“具体机制由批准记录固定并在实现阶段以隔离实测证明”。符合“未选定但禁止危险实现”。

### 3.5 RV-04 是否真关闭 —— **CLOSED**

### 3.6 `:3862` 新增边界概念 —— **OPEN**（`B13J-D03-RV2-01`，MEDIUM）

本轮新引入的整句：“整库 artifact 与这些受保护表的边界（排除相应 schema 或经隔离库后由 root 受控切换）同由批准记录固定。”

判定为**冲突且超范围**：

1. **与已固定的 restore 目标语义冲突。** `:3864` 规定 `target_connection` 只传“现役已校验 DSN”；`:3866` 规定“子程序必须对同一已校验 artifact/target 执行 restore”，root 复核“对同一目标/备份回执逐项一致”；`:3870` 要求同一 no-follow 稳定 fd。“经隔离库后由 root 受控切换”把替换目标变成隔离库、再由 root 搬进生产库，与上述三处同时不符。
2. **新增 root 的写权限通道。** `:3862` 明确“root 不代替执行”，ADR `:1007` 列出的 root 保留项为部署锁、排空/独占、Begin/绑定/审计与 `VerifyRestored` 判定，不含数据搬移。“root 受控切换”等于给 root 开一条绕开受审替换路径的直接写库通道，正是本轮要消除的那类路径。
3. **“identity/recovery 表”未定义且与整库还原不可同时成立。** `design.md:545` 把账号/业务数据与恢复元数据放在“同一 PostgreSQL 故障域”，`:1718` 的 `recovery_runs`/`recovery_restore_bindings` 也在同一 Store；`:3860` 要求 artifact 为单文件全量 SHA256/长度校验。于是“执行身份的目标 DB 角色不得覆盖 identity/recovery 表写入”要么使整库还原无法还原账号数据（还原的主要目的），要么要求 artifact 排除相应 schema——而排除后 `source_schema_digest`/`restored_schema_digest`（`:3860`、`:3866`）口径未定义。全文检索“身份表”0 命中，`:3862` 也未枚举受保护表清单。

连带影响：ADR `:1036` 把这句镜像成硬门禁（“该身份的目标 DB 角色写入 identity/recovery 表…均必须被拒绝”），按字面在真实整库还原下不可同时满足；ADR 不变量 `:1007`、约束 `:1024`、追溯 `:1045` 都未覆盖“隔离库/受控切换”，该能力在 ADR 侧无授权来源。

生产当前仍 closed（无现网暴露），但这是软件合同层的自相矛盾，且被写进解除门禁。

## 6. 评审结论

- **设计评审结论：CHANGES REQUIRED。** RV-01～RV-05 全部关闭，最小性、格式、追溯与继承边界均通过；但 `RV2-01` 使 `design.md:3862` 与其 `:3860`/`:3864`/`:3866`/`:3870` 的固定合同自相矛盾，属软件合同层缺陷，不能判 PASS。
- **安全评审结论：CHANGES REQUIRED。** gap-map §2.5 要求安全评审 PASS。`RV2-01` 既是权限边界问题（受保护表清单未定义、`:1036` 门禁不可满足），也是新增特权路径问题（root 受控切换绕过受审替换），安全门禁无法客观核验，故不 PASS。
- **总判定：CHANGES REQUIRED。**

- **可并入后续（D04 或下一轮）**：`B13J-D03-RV2-02`、`B13J-D03-RV2-03`。
