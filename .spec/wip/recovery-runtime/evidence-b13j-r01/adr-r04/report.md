## 3. ADR-0032 解除条件第 8 条自查（结论：不改）

评审 `F005` 把 `:1118` 列为「被架构与安全独立评审接受」的三处落点之一。核对后判定**不需要**同形否定，理由：

1. `:1118` 位于 ADR-0032 的「解除条件」第 8 条内，该条开篇即限定「解除必须按下列顺序逐节点留证」（`:1117`），作用面是**解除顺序**而非卡片登记入口；
2. 该节点自身已写「（决策级）；生产解除仍按约束 7」，与「评审接受 ≠ 生产解除」一致；
3. ADR-0032 正文没有「实施卡登记门禁」段落（其第 8 条不是登记门禁），因此不存在把「评审接受」误读为「人可以放行登记」的结构位；
4. 反证：若在此处再加否定句，反而会把「解除顺序中的一个节点」误标为「登记门禁」，与第 8 条开篇限定冲突。

故 ADR-0032 保持 `adr-0032-r03`（`:1068`），正文零改动。`R03-F005` 的关闭依据落在 `:960`(b) 与 `:1050`。

## 4. 语义论证

### 4.1 三级次序仍无环

`决策卡（无前置） → 决策修订被独立评审接受 → 实施/验证卡（产出真实证据） → 生产装配/解除卡 → 生产解除`。本轮只把每级的**语义**写清（登记 vs 解除、评审接受 vs 人的接纳），未增删节点、未改依赖方向，故无环性结论不变。

### 4.2 约束 7 的作用面现在是单一表述

`:953` 与 `:960`(c) 现在同口径：约束 7 只决定「能否解除 closed / 能否作生产可用声明」，不决定任何类别卡片能否登记。这消除了评审指出的「两处读法都可行」的歧义（严格读法＝最后才登记 S4.22；宽松读法＝可先登记）。

### 4.3 与 ADR-0032 解除链的兼容

ADR-0032 第 8 条要求 S4.22 requires S4.24b；本轮后 S4.22 的**登记**不再被约束 7 阻断，而其**解除**仍需约束 7 全项 + 人的批准，两者不冲突：链上每个节点都有可核前驱，`S4.22` 可以更早登记、仍只能在链尾解除。

### 4.4 未触碰 D03 的 restore 语义

本轮全部改动位于 ADR-0030 约束 7/9 与 ADR-0031 的「后续阶段前置节点」；`restore-v1`/`verify-v1` 软件合同、整库 restore 语义、执行身份写入边界（RV2-01 的「替换窗口内/外」两层）一字未改。
